# download-limiter

NebulaDrive 插件：按客户端 IP 限制下载频率，阻止批量抓取。

它挂在 `onAntiLeech` 钩子上，覆盖两条下载路径：

- 登录下载 `GET /api/files/:id/download`
- 公开分享下载 / 预览 `GET /api/shares/:id/download`、`/preview`

单个 IP 在任意 60 秒内超过 `maxPerMinute`，或在任意 60 分钟内超过
`maxPerHour`，插件返回：

```
blocked by download-limiter: 1 分钟内下载 31 次，超过上限 30（IP 203.0.113.7）
```

宿主据此返回 **403**。放行时插件返回空结果，不影响响应。

## 配置示例

```json
{
  "maxPerMinute": 30,
  "maxPerHour": 600,
  "exemptUserIds": [1, 2],
  "countSharePreview": false,
  "maxTrackedIPs": 10000
}
```

| 字段 | 默认值 | 说明 |
| --- | --- | --- |
| `maxPerMinute` | `60` | 单 IP 任意 60 秒内的下载次数上限 |
| `maxPerHour` | `1200` | 单 IP 任意 60 分钟内的下载次数上限 |
| `exemptUserIds` | `[]` | 豁免的**登录用户 ID**，命中者直接放行且不计数 |
| `countSharePreview` | `false` | 是否把公开分享的 `preview` 也计入下载次数 |
| `maxTrackedIPs` | `10000` | 同时跟踪的 IP 数上限，超出后淘汰最久未活动的 IP |

缺省或为 `0` 的字段使用默认值。配置解析失败时插件仍会启动，但改用默认配置，
并在 stderr 记一条 warn。

## ⚠️ 重要提醒：NAT / 公司出口 IP

按 IP 限流对**共享出口**很不友好。公司、学校、运营商 CGNAT 后面的大量用户
会共用一个公网 IP，他们会被算成同一个 IP、共用同一份额度 —— 一个人下载猛了，
整栋楼一起 403。这是按 IP 限流的固有代价。

上线前请评估：

1. **优先用 `exemptUserIds` 放行登录用户**（例如全部正式用户，
   或至少 VIP/管理员）。匿名分享访问者仍受限，批量抓取通常来自未登录的脚本，
   这样能显著降低误伤。
2. 站点用户都从同一出口访问时，把 `maxPerMinute` / `maxPerHour`
   调到与"出口总人数"匹配的量级，而不是按单个人估。
3. `countSharePreview: false` 会让分享页的内联预览不计数。若发现有人用预览
   接口拖库，把它改成 `true`。

## 滑动窗口语义

插件为每个 IP 保存最近 1 分钟与 1 小时的**时间戳队列**，每次判定前丢弃
过期时间戳，再做判断。这意味着：

- 任意长度为 60 秒的区间内，放行次数不超过 `maxPerMinute`；
  任意 60 分钟区间内不超过 `maxPerHour`。
- 不存在"整点清零"的固定窗口边界突刺（固定窗口在第 59 秒打满 N 次、
  第 61 秒再打满 N 次，实际 2 秒内过了 2N 次）。
- 被拦截的请求**不计数**。持续重试不会延长封禁，但也不会让窗口更快过去。
- 命中豁免（`exemptUserIds` / 预览 / 无 IP）的请求不计数。

## 内存上限

`maxTrackedIPs` 是安全边界，不是性能参数。没有它，攻击者用海量伪造 IP
每个只打一次，插件就会为每个 IP 建一份状态，内存随攻击流量增长 ——
限流器自己成了 DoS 面。

达到上限后，插件淘汰**最久未活动**的 IP。淘汰会连带清掉它的窗口计数，
所以攻击者若能用超过 `maxTrackedIPs` 个 IP 轮换，就能部分绕过按 IP 限流
（每次被重新跟踪时窗口从零开始）。需要更强防护时，请在上层（WAF / 反向代理）
再做一层全局限流，或降低 `maxTrackedIPs` 以换取更紧的内存占用。

## 命令行统计

```bash
nebula plugin download-limiter
```

输出当前窗口内的计数（按 1 分钟计数排序的 top 10 IP，含各自的 1 分钟 /
1 小时计数与最近活动时间），例如：

```
download-limiter 下载频率统计（跟踪 IP 3/10000；1 分钟上限 30，1 小时上限 600）
  #    IP                 1 分钟   1 小时   最近活动
  1    203.0.113.7        27       143      2026-10-18 16:12:03
  2    198.51.100.24      12       90       2026-10-18 16:11:55
  3    192.0.2.9          3        12       2026-10-18 16:10:41
```

统计只读，不影响限流状态。其他命令名不会触发本插件输出。

## 构建与安装

```bash
cd examples/plugins/download-limiter
go build -o download-limiter .        # Windows: -o download-limiter.exe
go vet ./...
go test ./... -count=1
```

把可执行文件与 `plugin.json` 放进宿主插件目录后在管理端启用即可。
插件声明 `minHostVersion: 26.10.0`、`protocolVersion: 1`，只使用标准库。

## 已知边界

- **计数只在内存里，重启清零。** 插件进程重启（宿主重启、插件重载、崩溃后
  被拉起）会丢失全部窗口状态，限流额度从零开始。这是刻意的：下载限流是
  热路径，每次请求落盘会把磁盘变成瓶颈；重启后短暂放开通常可以接受。
- **多副本部署时每个副本各自计数。** 若 NebulaDrive 以 N 个实例 + 负载均衡
  运行，每个实例上的插件都有独立状态，实际总限额是配置值的 **N 倍**，
  且请求被均衡到不同实例时窗口不连续。需要全局精确额度时，请在反向代理 /
  Redis 网关层做集中限流；本插件只适合单实例，或"每实例限额"可接受的场景。
- 插件只认宿主传入的 `ip` 字段。宿主取不到客户端 IP 时插件放行且不计数
  （宁可少拦，也不要在宿主某个调用点漏传字段时把全站下载拦死）。
- `shareKind=preview` 是否计数由 `countSharePreview` 控制；登录下载与
  `shareKind=download` 始终计数。
- 跟踪 IP 被淘汰后其窗口被重置（见上文「内存上限」）。
- 插件日志只在拦截时写一行 stderr（含 IP 与计数）。放行不记日志 ——
  下载是高频操作，逐次记录会瞬间淹没宿主给每个插件的 500 条环形缓冲。
