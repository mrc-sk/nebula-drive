NebulaDrive 插件开发 Wiki

适用版本：V26-10.0-d 及之后

读者：想给 NebulaDrive 写第三方插件的开发者，以及需要管理插件的管理员

本 Wiki 所有结论均从源码（backend/pkg/plugin/**、backend/controllers/plugins.go、examples/plugins/**）逐行核对得出。凡与代码不符之处，一律以代码为准。

这是什么

NebulaDrive 的插件系统让你不修改、不重编译主服务就能扩展它的能力：防盗链、HMAC 鉴权、SMTP 发信、备份镜像、协作跳转……都可以做成独立插件，热插拔、可独立崩溃。

插件以独立子进程运行，通过 stdin/stdout 上的 JSON-RPC 2.0 与主服务（宿主）通信。宿主在固定的「钩子（hook）」点调用插件，插件读 ctx、写回 ctxPatch、必要时用含 blocked 的 error 拦截请求。

01 · 架构

源码：backend/pkg/plugin/hooks.go、backend/pkg/plugin/host/manager.go、backend/pkg/plugin/host/proc_{windows,unix}.go

为什么是子进程，而不是 plugin.Open 或 WASM

方案结论
Go 原生 plugin.Open❌ 只支持 Linux/macOS 且需要 cgo；Windows 根本编译不了，且工具链/依赖版本一升级就可能让已构建的插件失效
WASM（wasmtime-go）❌ 需要 CGO，Go host function 绑定成本过高
独立子进程 + JSON-RPC over stdio✅ 跨平台、语言无关（插件可以用任何语言写）、崩溃隔离、真正热插拔

代价：每次调用多一次本地管道 IPC 往返（亚毫秒级）。

两种插件形态

业务代码对形态完全透明——只调 plugin.Fire(hook, ctx)，不关心 handler 在哪。

形态加载方式适用
进程外（主流）独立可执行文件，宿主拉起并通过 RPC 调用第三方扩展，可热插拔
进程内宿主二进制里 init() 调 plugin.Register内置功能，零 IPC 开销
混合两者同时存在，Fire 会先跑完进程内、再派发进程外常见：内置补核心能力，外部做扩展

进程内插件写法见 06-教程 §进程内插件；它改动要重编译主服务，不适合第三方。

派发模式：sync / async

每个钩子在 Hooks 表里标注 Mode：

模式行为适用
ModeSync阻塞等插件返回（超时 2s）业务要读结果才能决策：onAntiLeech（下载拦截）、onCollabOpen（302）、onApiAuth、onCLI
ModeAsync每插件一个 goroutine，结果不回传纯事件通知：邮件、审计、协作保存、备份/恢复事件、DB 迁移、限流事件

ModeAsync 不回写 ctx：业务已经继续往下走了，回写只会造成竞态。需要回传请用 ModeSync，或用 plugin.RateLimitGate() 强制同步（见 04-钩子 · onRateLimit）。

生命周期与隔离

能力状态
安装即用，不改源码、不重编译主服务✅
启用 = 拉起进程；禁用 = 杀进程；主服务不重启✅
崩溃隔离（崩溃只杀子进程，不影响宿主）✅
崩溃自动重启（指数退避，最长 5 分钟）✅
连续 5 次崩溃后停止并转人工✅
日志缓冲（每插件 500 条环形）✅
进程组隔离：Windows taskkill /T /F；Unix kill(-pgid)✅（避免孙进程变孤儿）

信任边界（重要）

插件与主服务同权等系统权限，没有沙箱。隔离靠的是「进程边界 + 权限自觉」，不是容器/沙箱。对第三方插件，安全保证来自 PBClus 签名 + 信任库，而非操作系统隔离。详见 05-安全与诚实边界。

02 · 清单 plugin.json

源码：backend/pkg/plugin/manifest.go（ParseManifest / Validate）

每个插件目录根下必须有一个 plugin.json。宿主加载时解析并逐字段校验；任何一项不合法直接拒载，错误信息含具体字段名，可直接展示给管理员。

全部字段

字段类型必需说明 / 校验
namestring✅唯一标识。[a-z0-9-_]，长度 2–64；不能以 -/_ 开头；不能是 Windows 保留名（CON/NUL/COM1…）。也是数据目录下的子目录名
titlestring展示名，≤128 字符；为空回退到 name
versionstring语义化版本 x.y.z（三段式，每段 ≤5 位数字）。空表示不限
authorstring作者名，≤64
descriptionstring一句话描述，≤512
entrystring✅可执行文件名。**必须是单个文件名，不能含 /、\、.. 或 `:*?"<>**。不带 .exe 即可跨平台通用（Windows 上自动补 .exe`）
args[]string传给可执行文件的参数，每条 ≤1024，禁止 NUL
envmap附加环境变量，会覆盖宿主同名变量——故不用于传敏感配置
protocolVersionint✅必须等于 1，否则拒载
hooks[]string✅声明本插件实现哪些钩子；不声明就不会被调用（避免被误用于没实现的钩子）。最多 32 个；必须是已知钩子名且不能重复
permissions[]string权限声明，仅供管理员安装前参考，宿主不强制、不校验（每条 ≤64）
licensestringSPDX 标识，≤64；空值默认 AGPL-3.0-only
homepagestring项目地址，≤256
minHostVersionstring最低宿主版本（x.y.z），空表示不限

全局限制：清单文件 ≤ 64 KB；未知字段会报错（json.Decoder.DisallowUnknownFields，拼错字段名不再静默生效）；字段长度超限、版本非法都会被精确拦截。

合法示例

{
  "name": "referer-guard",
  "title": "防盗链守卫",
  "version": "1.0.0",
  "author": "NebulaDrive",
  "description": "下载前校验 Referer，不在白名单内返回 403",
  "entry": "referer-guard",
  "args": [],
  "protocolVersion": 1,
  "hooks": ["onAntiLeech"],
  "permissions": ["read-download-metadata", "write-own-datadir"],
  "license": "AGPL-3.0-only"
}

常见校验失败

  • name 含大写 / 中文 → name 含非法字符（只允许小写字母、数字、-、_）
  • entry 写成 bin/myplugin 或 ..\x → entry 必须是单个文件名，不能含路径分隔符或 ..（这是安全红线，见下）
  • protocolVersion 写成 2 或漏写 → protocolVersion 不匹配：插件声明 2，宿主要求 1
  • hooks 写错成 onAntileech（大小写错） → 未知钩子 "onAntileech"（已知钩子见 04-钩子）

关于 entry 的硬约束

entry 会拼成 <插件目录>/<entry> 再交给 exec。若允许路径分隔符，manifest 就能让宿主执行插件目录外的任意文件——等于任意代码执行。所以不仅 Validate 挡，运行时 ExecPath 还会二次校验解析后路径确实落在插件目录内。

跨平台写法：清单里写 "entry": "myplugin"（不带后缀），Windows 上 ExecPath 会自动尝试 myplugin.exe；清单显式写了 .exe 但文件不存在时不会静默补（那是真缺文件）。

03 · 协议 JSON-RPC

源码：backend/pkg/plugin/manifest.go（RPC* 常量与结构）、backend/pkg/plugin/host/manager.go

协议极简：一行一个 JSON 对象，UTF-8，不做跨行分帧。插件日志走 stderr，绝不污染 stdout。

协议版本

ProtocolVersion = 1。清单 protocolVersion 必须与之相等，否则宿主拒载。

方法（method）

方法方向作用
init宿主→插件启动后插件必须主动等待这个请求才能工作。插件回 ok/hooks/version
fire宿主→插件一次钩子调用。参数 {hook, ctx, seq}
shutdown宿主→插件插件收到后应清理资源并退出进程
ping宿主→插件健康检查，插件应立即响应（如 {"pong":true}）
log插件→宿主通知：把一条日志发给宿主统一落库/转发。可选，更常见是写 stderr

init 参数与结果

// 宿主下发（init 的 params）
{
  "hostVersion": "V26-10.0-d",
  "hostProtocol": 1,
  "pluginName": "referer-guard",   // = manifest.name
  "dataDir": "/var/lib/nebula/plugins/referer-guard", // 已创建，可写；持久化放这里
  "config": { ... },               // 管理员填的配置（JSON 字符串反序列化后的对象）
  "startTimeoutMillis": 10000,
  "siteUrl": "https://disk.example.com"  // 可选，插件需要回调宿主时可用
}

// 插件返回（init 的 result）
{ "ok": true, "name": "referer-guard", "version": "1.0.0", "hooks": ["onAntiLeech"] }
// ok=false 时宿主会卸载并记录 error

插件不要去写宿主的数据目录，只写 dataDir。config 来是 plugins.config（JSON 字符串），安装后由管理员填写。

fire 参数与结果

// 宿主下发（fire 的 params）
{ "hook": "onAntiLeech", "ctx": { "userId": 1, "ip": "1.2.3.4", "referer": "https://a.com", "fileName": "x.zip" }, "seq": 7 }

// 插件返回（fire 的 result）
{
  "ctxPatch": { "refererGuard": "allowed" },  // 浅层合并，顶层键覆盖；不能删宿主已有键（要删请显式置 null）
  "error": "blocked by referer-guard: 外站访问"  // 含 "blocked" → 宿主把它转成可拦截请求的 error
}

致命细节：FireResult 没有 Blocked 布尔字段。拦截只能通过 error 文本包含子串 blocked（区分大小写）来表达。这与进程内插件的既有约定一致，两种形态拦截语义完全相同。

三条铁律（写插件必读）

  1. stdout 专供 RPC，一行一个 JSON。 日志一律写 stderr。混用会破坏分帧，插件直接失联。
  2. 唯一输出通道是 ctxPatch（浅层合并，顶层键覆盖）。 result 里没有「设置 ctx 字段」的语义，想改 ctx 就写 ctxPatch。
  3. 拦截用 error，且文本必须含小写 blocked。
    1. {"error": "blocked by x: 外网 IP"} → 403 ✅
    2. {"ctxPatch": {"blocked": true}} → 不会拦截 ❌

超时与兜底

常量值含义
DefaultStartTimeout10s启动 + init 往返预算
DefaultFireTimeout2s单次 fire 同步往返超时
单条日志≤2000 字符超出截断（按 rune 截断，不切坏 UTF-8）
一次响应日志行≤50 条超出丢弃

宿主对超时/崩溃做隔离与自动重启（见 01-架构）。插件侧应尽量快：把重活异步化，别在 fire 里同步做网络 IO 又卡满 2s。

最小可运行插件骨架（Go）

package main

import ("bufio"; "encoding/json"; "os")

func main() {
    sc := bufio.NewScanner(os.Stdin)
    for sc.Scan() {
        var req struct {
            ID int64 `json:"id"`; Method string `json:"method"`; Params json.RawMessage `json:"params"`
        }
        if json.Unmarshal(sc.Bytes(), &req) != nil { continue }
        switch req.Method {
        case "init":
            reply(req, map[string]any{"ok": true, "hooks": []string{"onAntiLeech"}}, nil)
        case "fire":
            reply(req, map[string]any{"ctxPatch": map[string]any{"ok": true}}, nil)
        case "shutdown":
            reply(req, map[string]any{"bye": true}, nil); return
        }
    }
}
func reply(req struct{ID int64 `json:"id"`}, result any, rerr any) { /* 序列化 + 写 stdout + '\n' */ }

插件不 import 宿主包：宿主与插件是独立进程，import 宿主会把整个后端拖进依赖图并造成版本耦合。协议结构在插件侧独立声明即可（参考 examples/plugins/*/main.go 顶部的「协议结构」段）。

04 · 钩子清单

源码：backend/pkg/plugin/hooks.go（Hooks 元信息表、HookModeOf、MetaOf）

钩子是宿主「在某某时机调用插件」的固定点。插件只在 plugin.json 的 hooks 里声明的钩子才会被派发。

总览（以当前代码为准）

钩子模式可拦截已接线用途
onAntiLeechsync✅✅下载/预览前触发，唯一下载拦截点，做防盗链必须用它
onCollabOpensync❌✅协作打开时触发；写 url 则 302 跳外部编辑器
onCollabSaveasync❌✅协作内容保存时触发，纯通知
onEmailasync❌✅创建站内通知时触发，纯通知。系统本身不含发信实现，此钩子是邮件外发唯一入口
onDBMigrateasync❌✅AutoMigrate + 版本迁移全部完成后触发，每次启动都触发（不只升级）
onRateLimitasync❌✅高频操作前触发（登录/上传/下载/分享增删/全局限流中间件）；拦截走 RateLimitGate
onBackupasync❌✅管理端创建备份之后触发，纯通知
onRestoreasync❌✅管理端提交恢复之前触发，纯通知（暂存制，恢复发生在下次启动）
onApiAuthsync✅✅内置鉴权（PAT/OAuth2）失败后触发，扩展鉴权方案
onCLIsync✅✅nebula plugin <cmd> [args...] 时触发，同步拿输出

⚠️ 旧文档（插件系统完全指南.md）曾把 onBackup/onRestore/onApiAuth/onCLI 标为「预留未接入」——那已过时。当前代码 Hooks 表里这 4 个均为 Wired: true，且已有对应调用点（backend/controllers/backup.go、middleware/api_auth.go、runPluginCLI）和示例插件。以本表与代码为准。

拦截的统一定义

全项目唯一的拦截判定：strings.Contains(err.Error(), "blocked")（区分大小写）。middleware/rate_limit.go、controllers/file.go 与进程外派发门都走 plugin.IsBlockedError。想拦截就必须让返回的 error 文本含小写 blocked。

onAntiLeech · 防盗链（sync / 可拦截）✅已接线

下载/预览前触发，覆盖两条路径：

  1. 登录下载 GET /api/files/:id/download
  2. 公开分享 GET /api/shares/:id/download 与 /preview
  • 登录下载 ctx：{userId, userName, ip, ua, fileId, fileName, referer}
  • 公开分享 ctx：{userId(恒为0), userName(恒为空), ip, ua, fileId, fileName, referer, shareId, shareKind, shareOwnerId}
  • shareKind 取值 download 或 preview——两者都是完整文件内容的出口，宿主一视同仁过闸；只想保护下载、放行本站分享页内联预览的插件，请自行按 shareKind 放行。
  • 返回 error 且文本含 blocked → 403。做防盗链必须用它。
  • ⚠️ 分享访问者是匿名的：userId 恒为 0，插件不能假设它有值，也不会像登录下载那样天然有「所有者」可比。

onRateLimit 的特殊处理

它在 7 处被调用，但只有限流中间件那一处需要读返回值做拦截决策。整个钩子设为 ModeSync 会让另外 6 处（登录/上传/下载/分享增删）每次白等 IPC 往返；保持 ModeAsync 又会让中间件拦截失效。

解决：钩子保持异步（不拖累热路径），限流中间件改调 plugin.RateLimitGate(ctx)——它走 Dispatcher.DispatchSync 强制同步等待。代价是最多一个 FireTimeout（默认 2s），且只在有插件声明了 onRateLimit 时才有实际等待；没有插件时立即返回空。

onCollabOpen · 协作打开（sync / 不可拦截）✅已接线

ctx = {userId, userName, fileId, fileName, mimeType, ip}。在 ctx 写入 url 字段则 302 跳转到该地址（OnlyOffice 等外部编辑器）。注意 ctx 是引用类型，异步派发时业务读 ctx 可能早于插件写入 → 竞态，故强制 sync。

onCollabSave · 协作保存（async / 不可拦截）✅已接线

ctx = {userId, userName, fileId, fileName, content}；content 是完整文件明文，大文件会显著增加内存占用。仅事件通知。

onEmail · 邮件外发（async / 不可拦截）✅已接线

ctx = {to, subject, body}，用户邮箱为空则不触发。系统本身不含任何发信实现，此钩子是邮件外发的唯一入口（示例：smtp-email、notify-webhook）。

onDBMigrate · 数据库迁移（async / 不可拦截）✅已接线

ctx = {fromVersion, toVersion}，两者相等表示本次无迁移。每次启动都会触发，不是「首次升级才触发」。插件建表必须幂等（CREATE TABLE IF NOT EXISTS），否则重复执行会报错。

onBackup · 备份后（async / 不可拦截）✅已接线

管理端创建备份之后触发。ctx = {kind, filename, size, sha256, dbPath, fileCount, createdAt, operator}。宿主负责生成备份包（SQLite 库 + 文件清单 manifest.json），插件可把它复制到 S3/异地或落审计。异步派发拿不到返回值，别指望用它否决备份。

onRestore · 恢复前（async / 不可拦截）✅已接线

管理端提交恢复之前触发。ctx = {filename, size, stagedPath, operator, currentDb}。用途是校验/审计/通知。⚠️ 恢复是暂存制：真正的库替换发生在下次启动（热替换正在使用的 SQLite 库不安全），所以插件在此拦不住这次恢复——需要否决请在管理端权限层解决。

onApiAuth · 开放 API 鉴权（sync / 可拦截）✅已接线

/api/v1/* 的内置鉴权（PAT/OAuth2）失败之后触发，用于扩展鉴权方案（HMAC 签名、IP 白名单、第三方令牌等）。

  • ctx = {method, path, query, ip, ua, headers, hasAuthorization, contentType, contentLength, bodyHash, bodyTruncated}
  • headers 不含 Authorization（内置凭据留在宿主，插件请用自己的头）。
  • 放行：在 ctx 写入 principalUserId（>0），宿主据此认定调用者身份。
  • 拒绝：返回含 blocked 的 error，宿主返回 403。
  • 两者都没有则视为未通过（fail closed）。
  • ⚠️ 内置鉴权成功时不会触发本钩子：既保证热路径零 IPC 开销，也意味着插件无法否决一个已有效的令牌——内置凭据始终优先。示例：hmac-auth。

onCLI · 命令行子命令（sync / 可拦截）✅已接线

执行 nebula plugin <cmd> [args...] 时触发，同步等待以便拿到输出。ctx = {command, args, argsRaw}；插件可写入 cliOutput（字符串，会被打印）与 cliExitCode（数字）。返回含 blocked 的 error 会让 CLI 以非 0 退出码结束。多个插件同时响应时 cliOutput 是后写覆盖，请自行加前缀区分。

05 · 签名与信任

源码：backend/pkg/plugin/pbclus/pbclus_sign.go、backend/pkg/plugin/pbclus/pbclus.go、backend/controllers/plugin_trust.go、backend/pkg/plugin/install/install.go

包格式逐字节规范见 ../PBClus-格式规范.md。

NebulaDrive 的插件分发格式叫 PBClus（v2）。一个 PBClus 包 = 头部 + 清单(plugin.json) + 载荷(目录) + 尾部(签名块)。安装器解包、校验签名，再交给 02-清单 解析。

一条必须先说清的事：签名 ≠ 可信

公钥内嵌在包里，所以任何人都能签一个合法的包：用自己的密钥签，再把公钥一起放进去，Valid 就是 true。「验证通过」只证明内容与签名自洽，不证明签名者是谁、也不证明你要信任它。

安全语义完全来自宿主侧的信任库（keyId 白名单）：只有 Trusted 才有意义。安装决策只能用 Trusted，用 Valid 做决策等于没校验——这是这类设计最常见也最危险的误用，所以代码把两个状态拆成两个字段，不给「顺手用错」留空间。

三种签名状态

字段含义
present包里是否有签名块
valid签名与内容是否自洽（不代表可信）
trusted签名者的 keyId 是否在宿主的信任库里

valid 的判定：签名消息 = 域分隔前缀 PBClus/v2 signed-package\n ‖ 文件 SHA-256；用内嵌公钥做 Ed25519 验证。缺少 Verify() 步骤时攻击者可以改内容同时改 SHA，签名照样「通过」，所以安装前必须先 Verify 再读状态。

KeyID 与密钥

  • 算法：Ed25519（当前唯一，SigAlgEd25519 = 1）。
  • KeyID = 公钥 SHA-256 的前 8 字节的十六进制（16 个字符）。用 8 字节而非 32：keyId 是给人看、给人抄的（管理员第一次信任发布者时要能一眼比对），在「插件发布者数量」量级上碰撞可忽略。
  • SigningKey 结构：name / privateKey(64 字节 base64) / publicKey(32 字节 base64) / keyId。
  • 生成：pbclus.GenerateSigningKey(name)；保存：Save(path) 权限 0600（这是能签出「被信任包」的私钥，泄漏等于别人可冒充该发布者；Windows 不认 POSIX 位，文档另提醒别把私钥提交进版本库）。

公钥分发文件 .pub.json

keygen 会额外写一个 <名字>.pub.json，专门交给管理员：

{ "keyId": "...", "name": "NebulaDrive", "algorithm": "ed25519",
  "publicKey": "base64...", "notice": "这是公钥，可公开；私钥在另一个文件，绝不要发送或提交它。" }

为什么要单独一个只有公钥、名字里就写着 pub 的文件：私钥文件里同时含私钥与公钥，而「把你的密钥文件发给我」是极自然的表达——一旦照做就是私钥泄漏。给一个只有公钥的文件能把这条歧义堵住。

信任库（TrustStore）

信任库是 keyId → 名称 的白名单（KeyRing，字段 keys: [{keyId, name, publicKey?, addedAt}]）。建立信任的唯一推荐入口是 TrustRecordFromPublicKey(pubBase64, name)：keyId 由公钥推导，两者必然自洽，从根上排除「keyId 写的是可信发布者、公钥却是别人的」替换。也允许 TrustRecordFromKeyID(keyId, name)（发布者只公布了 keyId 时），但不如给公钥安全：keyId 是公钥摘要，无法反向校验，挡不住「同一 keyId 配了别人的公钥」。

信任库自身 Validate() 会校验：keyId 长度 16 且为十六进制、不重复、填了 publicKey 就必须与 keyId 自洽。

三种签名策略（trustMode）

模式行为
off关闭签名检查。任何包都能安装，界面也不再提示签名状态
warn（默认）照常安装，但会提示签名状态
require只接受受信任签名的包。没有信任任何发布者时，所有 PBClus 包都会被拒绝

改 require 前的诚实提示：存量无签名插件会让新安装全部被拒（已安装的不受影响）。接口在「有存量无签名插件」时要求带 confirm=true 才放行。

管理接口（见 08-管理端）

  • GET /api/admin/plugins/trust — 查策略 + 信任库内容 + 已安装/已签名/已信任计数
  • POST /api/admin/plugins/trust/key — 加一枚公钥（只收 publicKey 或 keyId，明确拒绝私钥）
  • DELETE /api/admin/plugins/trust/:keyId — 移除一枚公钥（撤销的唯一手段；已安装的插件不会被自动卸载）
  • PUT /api/admin/plugins/trust/mode — 改策略（off/warn/require，require 需 confirm）

安全与诚实边界

  • 插件没有沙箱：与主服务同权系统权限，隔离靠进程边界 + 权限自觉，不是容器。
  • permissions 声明不强制：只展示给管理员看，宿主不校验。
  • valid 不等于 trusted：安装决策只用 trusted。
  • 商店条目 version/author 不可信：真实清单以下载后的 plugin.json 为准。
  • 别把私钥发到任何地方：接口只收公钥；私钥文件权限 0600 且严禁提交版本库。

06 · 上手教程

跟着做一遍，你就能拥有一个可运行的插件。完整可参考 examples/plugins/referer-guard/。

目标

写一个最小防盗链插件：在 onAntiLeech 里，Referer 不在白名单就返回含 blocked 的 error（→ 403）。

步骤 1 · 建目录与清单

mkdir myplugin && cd myplugin

plugin.json：

{
  "name": "myplugin",
  "title": "我的第一个插件",
  "version": "1.0.0",
  "author": "你",
  "description": "Referer 在白名单外就拦截",
  "entry": "myplugin",
  "protocolVersion": 1,
  "hooks": ["onAntiLeech"],
  "permissions": ["read-download-metadata"]
}

步骤 2 · 写 main.go

package main

import (
    "bufio"; "encoding/json"; "fmt"; "os"; "strings"
)

func main() {
    sc := bufio.NewScanner(os.Stdin)
    for sc.Scan() {
        var req struct {
            ID int64 `json:"id"`; Method string `json:"method"`; Params json.RawMessage `json:"params"`
        }
        if json.Unmarshal(sc.Bytes(), &req) != nil { continue }
        switch req.Method {
        case "init":
            reply(req, map[string]any{"ok": true, "hooks": []string{"onAntiLeech"}}, nil)
        case "fire":
            var p struct {
                Hook string `json:"hook"`; Ctx map[string]any `json:"ctx"`
            }
            json.Unmarshal(req.Params, &p)
            allow := false
            if ref, _ := p.Ctx["referer"].(string); strings.HasPrefix(ref, "https://trusted.example.com") {
                allow = true
            }
            res := map[string]any{}
            if !allow {
                res["error"] = "blocked by myplugin: 外站 Referer " + fmt.Sprint(p.Ctx["referer"])
            }
            reply(req, res, nil)
        case "shutdown":
            reply(req, map[string]any{"bye": true}, nil); return
        }
    }
}

func reply(req struct{ ID int64 `json:"id"` }, result any, rerr any) {
    m := map[string]any{"jsonrpc": "2.0", "id": req.ID, "result": result}
    b, _ := json.Marshal(m)
    os.Stdout.Write(append(b, '\n'))
}

真实项目里把协议结构（request/response/initParams/fireParams/fireResult）单独声明并复用，别每次手写——examples/plugins/*/main.go 顶部有可直接抄的版本。

步骤 3 · 构建

go build -o myplugin .          # Windows: -o myplugin.exe .

不限于 Go：任何语言能读写 stdin/stdout 的 JSON 行即可。只要实现了 init/fire/shutdown 循环，并遵守 03-协议 的三条铁律。

步骤 4 · 安装

两种方式：

  • 本地目录（开发最方便）：管理端「插件 → 安装」，选 source=local，path 填该目录绝对路径；或直接 POST /api/admin/plugins/install {"source":"local","path":"/abs/myplugin"}。
  • URL / 商店：source=url 填 zip 地址（仅允许 http/https）。

安装不会自动启用——必须显式点「启用」。这是刻意的：否则「阅读并同意插件协议」那一步形同虚设。首次进插件页会弹协议，必须滚动到底才能勾选，且后端 requireAgreement 强制（未同意时安装/启用接口直接 403，只靠前端弹窗可被 API 绕过）。

步骤 5 · 启用 + 配置

启用后插件进程被拉起。onAntiLeech 不需要配置即可工作；如果需要配置，在插件页（或 PUT /api/admin/plugins/:name/config）填 JSON，重启后生效。配置不要放敏感值到 env（env 会覆盖宿主变量）。

步骤 6 · 看日志 / 调试

  • 插件日志：GET /api/admin/plugins/logs?name=myplugin&limit=200（每插件 500 条环形缓冲）。
  • 协议关卡失败、init 返回 ok=false、启动超 10s、单次 fire 超 2s、崩溃 5 次 → 都会在列表的 status/error 字段暴露。
  • 经典坑：entry 写成带路径的、protocolVersion 写错、hooks 拼错大小写 → 直接拒载，看列表错误信息即可定位。
  • 进程外插件崩溃只杀子进程，宿主会指数退避自动重启（最长 5 分钟）。

进程内插件（内置功能）

改动要重编译主服务，适合内置能力，不适合第三方。写法：

package plugin // backend/pkg/plugin/custom/ 下

func init() {
    Register(HookAntiLeech, func(ctx map[string]any) (map[string]any, error) {
        defer func() { recover() }() // 必须，进程内 panic 会炸请求
        return nil, nil
    })
}

注意：ctx 字段必须带类型断言（ctx["userId"].(uint) 实际是 float64 会 panic）；不要在 handler 里调 Register（旧实现持锁会死锁）；ctx 被同钩子所有 handler 共享，恶意/有 bug 的插件可篡改后续所见数据。

07 · 官方示例

全部位于 examples/plugins/，每个目录含 plugin.json + main.go + go.mod（+ 多数有 README.md / main_test.go）。版本均为 1.0.0，可直接 go build 后本地安装。

示例钩子做什么
referer-guardonAntiLeech下载前校验 Referer，不在白名单内返回 403。支持通配符与正则模式，记录下载审计。最完整的「拦截型」范例
download-limiteronAntiLeech, onCLI按客户端 IP 做滑动窗口下载限流（1 分钟/1 小时双阈值），超出 403。支持登录用户豁免、分享预览豁免
hmac-authonApiAuth为 /api/v1/* 提供 PAT/OAuth2 之外的 HMAC-SHA256 签名鉴权；校验通过认定调用者身份，签名不符或时间戳超窗一律拒绝
smtp-emailonEmail把站内通知通过 SMTP 投递到用户邮箱；支持 starttls/implicit/none 三种 TLS，中文主题正文正确编码
notify-webhookonEmail, onCLI把站内通知转发到 Slack、飞书、钉钉、Discord 或任意通用 webhook；URL 日志脱敏，超时控制，5xx 自动重试一次
backup-mirroronBackup, onRestore, onCLI把宿主生成的备份包流式镜像到多个异地目录，按保留数轮转，并把恢复操作追加进本地审计日志
collab-redirectonCollabOpen, onCLI按扩展名或 MIME 前缀判断文件是否交外部编辑器，命中时把协作打开 302 跳转到模板化编辑器地址（只做跳转，不代理文件、不做鉴权）

推荐阅读顺序

  1. 想写拦截型插件 → referer-guard（看 init/fire/shutdown 循环 + blocked 用法 + ctx 数字字段的 float64 类型断言坑）。
  2. 想写异步事件型插件 → smtp-email / notify-webhook（看 onEmail 的 ctx 用法、网络失败重试）。
  3. 想写扩展鉴权 → hmac-auth（看 onApiAuth 的 principalUserId 放行 + 时间窗防重放 + 常量时间比较）。
  4. 想写 CLI 子命令 → 任意带 onCLI 的示例（看 cliOutput/cliExitCode 回写）。

插件协议关卡（agreement）

  • 首次进入插件页弹窗，要求阅读并同意。
  • 必须滚动到底才能勾选——一打开就能点同意等于没要求同意。
  • 后端强制（requireAgreement）：未同意时安装/启用接口直接 403。只靠前端弹窗的话，直接调 API 就能绕过。
  • 协议正文硬编码在 pkg/plugin/agreement.go，不从配置文件读（避免部署者改掉管理员看到的内容）。协议升级后需重新同意。

最容易被忽略的坑

安装 / 启用成功后，列表会暴露「数据库说启用但进程没跑」的矛盾——管理员会看到「已启用」却毫无效果。先查列表的 status/error，再看 /logs；多半是 entry 拼错、init 返回 ok=false、或启动超 10s。
