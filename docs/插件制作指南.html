NebulaDrive 插件制作指南

教你从零写一个能在 NebulaDrive 里跑起来的插件。所有结论都从当前源码逐行核对得出 —— 凡与代码不符之处，以代码为准。

读完你会得到

一个可编译、可安装、可热插拔的插件可执行文件；知道每个钩子什么时候触发、能拿到什么字段、 怎么拦截请求；以及出问题时该看哪里。

0 · 先读这一页

插件长什么样

插件就是一个独立的可执行文件，放在自己的目录里，旁边有一份 plugin.json。宿主把它当子进程拉起来，通过 stdin/stdout 上的 JSON-RPC 2.0 跟它对话。

🔌 语言无关

任何能读写 stdin/stdout 的语言都行：Go、Python、Node、Rust、甚至 shell。

🔥 真热插拔

启用 = 拉起进程，禁用 = 杀进程。主服务不重启、不断连。

🧱 崩溃隔离

插件崩了只杀它自己。连续 5 次崩溃后停止自动重启，转人工。

⚠️ 没有沙箱

插件以宿主同等系统权限运行。隔离靠进程边界 + 你的自觉。

三种「插件」形态，别搞混

形态怎么加载适合要重编译主服务吗
进程外（本指南主题）独立可执行文件，宿主拉起并 RPC 调用第三方扩展不需要
进程内主服务二进制里 init() 调 plugin.Register内置功能需要

业务代码对两种形态完全透明 —— 它只调 plugin.Fire()，不关心 handler 在哪。

60 秒流程

  1. 写代码实现一个可执行文件：读 stdin 的 JSON-RPC，把响应写回 stdout，日志写 stderr。
  2. 写 plugin.json声明名字、入口、实现了哪些钩子。
  3. 编译go build -o 你的插件名 .（Windows 会自动补 .exe）。
  4. 安装管理端 → 插件 → 用本地目录或 zip URL 安装。
  5. 启用点「启用」拉起子进程。安装不会自动启用。

1 · 快速上手

1.1 plugin.json

放在插件目录根下，与可执行文件同级。

{
  "name": "myplugin",
  "title": "我的插件",
  "version": "1.0.0",
  "author": "你的名字",
  "description": "一句话说明这个插件做什么",
  "entry": "myplugin",
  "args": [],
  "protocolVersion": 1,
  "hooks": ["onAntiLeech"],
  "permissions": ["read-download-metadata", "write-own-datadir"],
  "license": "AGPL-3.0-only"
}
字段必需规则
name必需唯一标识。只允许小写字母、数字、-、_，2–64 字符，不能以 -/_ 开头。它会成为数据目录名。
entry必需可执行文件名。不带 .exe 即可跨平台通用（Windows 会自动补）。
protocolVersion必需必须等于 1，不匹配直接拒载。
hooks必需声明实现哪些钩子，至少 1 个，不能重复。没声明的钩子不会被派发。
version可选语义化三段式 x.y.z，纯数字。
title/author/description可选管理端展示用。建议都填。
permissions可选仅供展示宿主不校验。它的价值是让管理员安装前知道你要什么。
args / env可选传给子进程的参数与环境变量。env 会覆盖宿主同名变量，别用它传密钥。
minHostVersion可选最低宿主版本，如 26.10.0。留空不限。
license可选SPDX 标识，默认 AGPL-3.0-only。
🚫 两个会让你装不上的错误
  • 未知字段直接报错。清单解析开了「拒绝未知字段」，拼错一个键名（"hook" 少个 s）整份清单就废了。
  • entry 不能含路径分隔符或 ..。这不是形式主义：宿主会把 <插件目录>/<entry> 交给 exec，允许分隔符等于让清单指定插件目录外的任意可执行文件。

1.2 RPC 协议

每行一个 JSON 对象，UTF-8，不跨行分帧。宿主 → 插件有 4 个方法：

方法方向说明
init宿主 → 插件启动后第一件事。返回 {"ok":true} 才算就绪；ok:false 会被卸载并记录原因。
fire宿主 → 插件触发钩子。params = {hook, ctx, seq}。
ping宿主 → 插件健康检查，立刻回 {"pong":true}。
shutdown宿主 → 插件清理资源后退出进程。

init 下发的参数

字段类型用途
hostVersionstring宿主版本串，如 V26-10.0-d。
hostProtocolint协议版本。必须校验，不匹配要明确失败而不是勉强跑。
pluginNamestring宿主侧的插件标识。
dataDirstring插件专属可写目录，已创建。持久化都放这里，不要写宿主数据目录。
configobject你在管理端填的配置。没配过时可能缺省。
siteURLstring站点根 URL，回调宿主时用。
startTimeoutMillisint你的启动预算（默认 10000ms）。

fire 的结果

{
  "ctxPatch": { "myFlag": true },   // 唯一输出通道，浅层合并（顶层键覆盖）
  "error": "blocked by myplugin: 原因"        // 含 "blocked" 才会被宿主当作拦截
}
⚠️ result 里没有「设置 ctx 字段」这种语义

想回传数据只能写 ctxPatch。 写 {"userId": 1} 是无效的，宿主不会读。

1.3 可编译骨架（Go）

插件不 import 宿主包 —— 宿主与插件是两个 module， 共享依赖会造成版本耦合，也会把整个后端拖进插件的依赖图。 代价是协议结构要自己抄一遍，下面这份拿去就能用。 

package main

import (
	"bufio"
	"encoding/json"
	"fmt"
	"os"
)

// ---- 协议结构：与宿主 pkg/plugin 保持一致 ----
type rpcError struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
}

type request struct {
	JSONRPC string          `json:"jsonrpc"`
	ID      int64           `json:"id"`
	Method  string          `json:"method"`
	Params  json.RawMessage `json:"params"`
}

type response struct {
	JSONRPC string          `json:"jsonrpc"`
	ID      int64           `json:"id"`
	Result  any             `json:"result,omitempty"`
	Error   *rpcError       `json:"error,omitempty"`
}

type initParams struct {
	HostVersion  string          `json:"hostVersion"`
	HostProtocol int             `json:"hostProtocol"`
	PluginName   string          `json:"pluginName"`
	DataDir      string          `json:"dataDir"`
	Config       json.RawMessage `json:"config"`
	SiteURL      string          `json:"siteUrl"`
}

type fireParams struct {
	Hook string         `json:"hook"`
	Ctx  map[string]any `json:"ctx"`
	Seq  int64          `json:"seq"`
}

type fireResult struct {
	CtxPatch map[string]any `json:"ctxPatch,omitempty"`
	Error    string         `json:"error,omitempty"`
}

const hookAntiLeech = "onAntiLeech"

func main() {
	sc := bufio.NewScanner(os.Stdin)
	sc.Buffer(make([]byte, 0, 64*1024), 8<<20)

	for sc.Scan() {
		line := sc.Bytes()
		if len(line) == 0 {
			continue
		}
		var req request
		if err := json.Unmarshal(line, &req); err != nil {
			// 宿主写出的行必须是合法 JSON；解析不了说明协议层有问题，
			// 但插件不能因此退出（否则宿主看不到原因）。
			logf("无法解析请求: %v", err)
			continue
		}
		switch req.Method {
		case "init":
			handleInit(req)
		case "fire":
			handleFire(req)
		case "ping":
			reply(req, map[string]any{"pong": true}, nil)
		case "shutdown":
			reply(req, map[string]any{"bye": true}, nil)
			return
		default:
			reply(req, nil, &rpcError{Code: -32601, Message: "不支持的方法: " + req.Method})
		}
	}
}

func handleInit(req request) {
	var p initParams
	if err := json.Unmarshal(req.Params, &p); err != nil {
		reply(req, map[string]any{"ok": false, "error": err.Error()}, nil)
		return
	}
	if p.HostProtocol != 1 {
		// 明确失败比「勉强跑起来」好：协议不匹配时静默降级会出难查的问题
		reply(req, map[string]any{
			"ok":    false,
			"error": fmt.Sprintf("协议版本不匹配：宿主 %d，插件只支持 1", p.HostProtocol),
		}, nil)
		return
	}
	logf("就绪：宿主 %s，数据目录 %s", p.HostVersion, p.DataDir)
	reply(req, map[string]any{
		"ok": true, "name": "myplugin", "version": "1.0.0",
		"hooks": []string{hookAntiLeech},
	}, nil)
}

func handleFire(req request) {
	var p fireParams
	if err := json.Unmarshal(req.Params, &p); err != nil {
		reply(req, nil, &rpcError{Code: -32602, Message: err.Error()})
		return
	}
	if p.Hook != hookAntiLeech {
		reply(req, fireResult{}, nil)
		return
	}

	// ctx 经 JSON 往返后数字一律是 float64 —— 断言 int 会永远失败，
	// 而且不报错。这是插件里最常见的一类「静默不生效」。
	ref, _ := p.Ctx["referer"].(string)
	name, _ := p.Ctx["fileName"].(string)
	if ref == "" {
		reply(req, fireResult{CtxPatch: map[string]any{"myFlag": "allow"}}, nil)
		return
	}
	reply(req, fireResult{
		// 必须含 "blocked"，宿主据此返回 403
		Error:    fmt.Sprintf("blocked by myplugin: %s 的 Referer 是 %s", name, ref),
		CtxPatch: map[string]any{"myFlag": "block"},
	}, nil)
}

func reply(req request, result any, rerr *rpcError) {
	out := response{JSONRPC: "2.0", ID: req.ID, Result: result, Error: rerr}
	b, err := json.Marshal(out)
	if err != nil {
		logf("序列化响应失败: %v", err)
		return
	}
	os.Stdout.Write(append(b, '\n'))
}

// logf 日志必须走 stderr：stdout 是 RPC 专用通道。
// 宿主会把 stderr 收进插件日志缓冲，在管理端「查看日志」里能看到。
func logf(format string, args ...any) {
	fmt.Fprintf(os.Stderr, "[myplugin] "+format+"\n", args...)
}

自动启用会让「阅读并同意插件协议」这一步形同虚设。 首次安装/启用前必须先读过协议 —— 后端强制，未同意时接口直接 403， 不是只靠前端弹窗。

2 · 钩子参考

这是当前的完整钩子表。没有 Wired:false 的钩子了 —— 下面每一个都真的有触发点。

钩子模式可拦截触发时机
onAntiLeechsync可拦截登录下载、分享下载与分享预览之前
onCollabOpensync—打开协作编辑时（写 url 可 302 跳转）
onApiAuthsync可拦截开放 API 内置鉴权失败之后
onCLIsync可拦截执行 nebula plugin <cmd> 时
onEmailasync—创建站内通知时
onRateLimitasync见下高频操作前（7 个调用点）
onDBMigrateasync—每次启动迁移完成后
onBackupasync—管理端创建备份之后
onRestoreasync—管理端提交恢复之前
onCollabSaveasync—保存协作内容时（含完整文件明文）

模式意味着什么

模式宿主行为你能做什么
sync阻塞等你返回，超时 2 秒能回传数据（ctxPatch），能拦截（error）。别在这里做慢操作。
async每个插件一个 goroutine，结果直接丢弃只能当事件通知用。写 ctxPatch 不会有人读，返回 error 也不会拦截。
⚠️ 异步钩子拿不到返回值 —— 这是设计，不是 bug

业务在派发异步钩子后已经继续往下走了，回写 ctx 只会造成竞态。 所以「在 onEmail 里返回 error 来阻止通知创建」是做不到的。 需要否决能力请用同步钩子。

各钩子的 ctx 契约

onAntiLeech — 防盗链 可拦截

两条路径的字段不同，插件必须都处理：

来源ctx
登录下载{userId, userName, ip, ua, fileId, fileName, referer}
公开分享{userId(恒为0), userName(恒为空), ip, ua, fileId, fileName, referer, shareId, shareKind, shareOwnerId}
  • shareKind 是 "download" 或 "preview"。
  • 预览也是完整文件内容的出口，宿主对两者一视同仁地过闸。只想保护下载、放行本站分享页内联预览的插件，请自行按 shareKind 放行。
  • 分享访问者是匿名的：userId 恒为 0 且键一定存在。不要用它做豁免判断。
  • 想放行豁免用户，请判断 userId > 0 && userId 在豁免列表。

onApiAuth — 扩展鉴权 可拦截

内置鉴权（PAT / OAuth2）都失败之后才触发，包括「根本没带 Authorization」的请求。

ctx 字段说明
method / path / query请求行三要素。query 是原始串，未规范化。
headers全部请求头，不含 Authorization（内置凭据留在宿主）。用你自己的头传签名。
hasAuthorization是否带了 Authorization，布尔。
contentType / contentLength请求体信息。
bodyHash"sha256:<hex>"。请求体超过 64KB 时为空串。
bodyTruncatedtrue 表示宿主没读完 body，此时不要放行 —— 你无法校验完整性。
ip / ua来源信息，用于审计。

两种表达方式，二选一：

// 放行：在 ctxPatch 里写 principalUserId（必须 > 0 且是真实存在的用户 ID）
{"ctxPatch": {"principalUserId": 42}}

// 拒绝：返回含 "blocked" 的 error，宿主回 403
{"error": "blocked by myauth: 签名不匹配"}

// 两者都没有 → 宿主按未通过处理（保持 401）
🚫 别在 onApiAuth 里「没意见」地退回

如果你装了插件但配错了（比如没填密钥），正确行为是拒绝一切。 退回「没意见」看起来无害，但那样任何人都能靠不带签名头绕过你的保护。 要放行的公开端点，请显式列进配置的免签列表。

onCLI — 自定义命令行 可拦截

执行 nebula plugin <cmd> [args...] 时触发。

ctx 字段说明
command子命令名，如 "hello"。
args参数数组。
argsRaw参数拼成的原始串。

回传方式（经 ctxPatch）：

{
  "ctxPatch": {
    "cliOutput": "我的插件收到了 hello\n",   // 会打印到 stdout
    "cliExitCode": 0                          // 非 0 会让命令行以该码退出
  }
}

退出码约定：0 成功 · 1 用法错误或被插件拒绝 · 2 系统未安装。

⚠️ 多个插件响应同一命令时 cliOutput 是后写覆盖

请自行加前缀区分（例如 [myplugin] ...），否则输出会互相覆盖。

onEmail — 邮件外发

{to, subject, body}。用户邮箱为空时不会触发。

💡 这是邮件外发的唯一入口

宿主本身不含任何发信实现（全仓没有 net/smtp 调用）。没有邮件插件，站内通知永远到不了邮箱。官方示例见 examples/plugins/smtp-email/。

onBackup / onRestore — 备份恢复

钩子ctx时机
onBackup{kind, filename, path, size, sha256, dbPath, dbIncluded, fileCount, createdAt, operator}备份包生成之后。可据此复制到 S3 / 异地或落审计。
onRestore{filename, size, stagedPath, currentDb, operator}恢复提交时。仅通知。
🚫 恢复是「暂存制」，这两个钩子都拦不住它

真正的数据库替换发生在下次启动（热替换正在被使用的 SQLite 库会损坏数据）。 两个钩子都是异步的，拿不到否决权。需要拦住恢复请在权限层解决。

onDBMigrate — 建表

{fromVersion, toVersion}。每次启动都会触发，不只升级时。两者相等表示本次没有迁移。

⚠️ 你的建表语句必须幂等

用 CREATE TABLE IF NOT EXISTS 之类。否则第二次启动就会报错 —— 而这个钩子每次启动都跑。

onRateLimit — 限流的特殊情况

它在 7 个地方被调用，但只有限流中间件那一处会读返回值。 为了不让另外 6 处（登录/上传/下载/分享增删）每次白等一次 IPC 往返， 这个钩子整体是异步的，中间件那一处改走一个强制同步的入口。

结论：想拦请求请用 onAntiLeech，别指望 onRateLimit。

3 · ctx 字段字典

🚫 最重要的一条：数字都是 float64

ctx 经 JSON 往返之后，所有数字都是 float64。 ctx["userId"].(int) 或 .(uint) 会静默失败 —— 不 panic（用带 ok 的断言时），功能就是不生效，而且没有任何报错。 

// ❌ 错：永远拿不到值，且不报错
if id, ok := ctx["userId"].(uint); ok { ... }

// ✅ 对：写一个兼容多种来源的取值函数
func numOf(v any) (uint64, bool) {
	switch n := v.(type) {
	case float64:   // JSON 往返后的常态
		if n >= 0 { return uint64(n), true }
	case int:
		if n >= 0 { return uint64(n), true }
	case int64:
		if n >= 0 { return uint64(n), true }
	case uint64:
		return n, true
	case uint:
		return uint64(n), true
	}
	return 0, false
}

// 字符串直接断言即可（JSON 里字符串就是字符串）
name, _ := ctx["fileName"].(string)

// headers 是个 map —— 但要注意它的值类型取决于来源
func headerValue(ctx map[string]any, name string) (string, bool) {
	switch hs := ctx["headers"].(type) {
	case map[string]string:  // 进程内 handler 传的形态
		for k, v := range hs {
			if strings.EqualFold(k, name) { return v, true }
		}
	case map[string]any:  // JSON 往返后的形态
		for k, v := range hs {
			if strings.EqualFold(k, name) { return fmt.Sprint(v), true }
		}
	}
	return "", false
}

通用字段一览

字段类型出现在说明
userIdfloat64多数钩子用户 ID。分享场景恒为 0。
userNamestring多数钩子用户名。分享场景为空串。
ipstring多数钩子客户端 IP。
uastring多数钩子User-Agent。
fileId / fileNamefloat64 / string文件相关钩子文件 ID 与名字。fileName 是不可信输入，用过它拼路径就完蛋了。
refererstringonAntiLeechReferer 头原值，可能为空。
shareId / shareKind / shareOwnerIdfloat64 / string / float64onAntiLeech（分享路径）分享标识、场景、分享所有者（与访问者不是一回事）。

宿主会给插件子进程设 NEBULA_PLUGIN_DATA 指向数据目录，与 init 里的 dataDir 一致。

4 · 常见配方

配方一：防盗链（Referer 白名单）

完整可运行版本见 examples/plugins/referer-guard/。要点：

  • 支持三种规则写法：前缀、*.example.com 通配、re: 开头的正则。
  • 正则要预编译。每次请求现编译是一个 DoS 面。
  • 默认放行无 Referer 的请求 —— 很多下载工具（curl/wget）不带 Referer，一律拦会打断自己人用命令行取文件。
  • 豁免用户判断要先确认 userId > 0，否则分享链接会被当成「用户 0」而误判。

配方二：HMAC 签名鉴权

完整版本见 examples/plugins/hmac-auth/。待签名规范串：

METHOD\nPATH\nQUERY\nTIMESTAMP\nBODY_SHA256_HEX
  • 五行缺一不可。少任何一行，攻击者就能在不改签名的前提下替换那部分内容。
  • METHOD 统一大写（同时接受大小写会让签名含义模糊）。
  • 空 body 也要算摘要，值是 e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855。
  • 用常量时间比较（hmac.Equal / 等价实现）。用 == 会在第一个不同字节处返回，可以被逐字节猜出签名。
  • 时间窗是防重放的唯一手段 —— 签名是静态的，没有时间窗就能被无限重放。

		// 解析失败退回默认而不是拒绝启动：插件不该因为配置笔误就完全不可用。
		// 但一定要记日志说清楚。

		}
	}
	if cfg.TimeoutSeconds <= 0 {
		cfg.TimeoutSeconds = 10   // 零值兜底：context.WithTimeout(0) 会立即过期
	}
	return cfg
}

6 · 硬性规则

这几条违反任何一条都会出问题，而且症状通常很难查。

1. stdout 只放 RPC

一行一个 JSON。日志一律 stderr。混用会破坏分帧 —— 插件直接失联，宿主只看到「进程没响应」。

2. 拦截只认 error + "blocked"

必须从小写 blocked 子串。写 ctxPatch:{"blocked":true} 无效，大写不匹配。

3. 数字当 float64 读

ctx 经 JSON 往返。断言成 int/uint 会静默失效。

4. 只写自己的 dataDir

init 给的 dataDir 是你的可写目录。别去写宿主数据目录。

5. init 必须校验协议版本

不匹配要明确失败。静默降级会出难查的语义错误。

6. 密钥不进日志

插件日志展示在管理端。打日志前脱敏。

7. 同步钩子要快

同步钩子超时 2 秒。超时会拖慢真实用户请求。

8. 幂等建表

onDBMigrate 每次启动都触发，不是只升级时。

10 · PBClus 插件包格式

除 zip 之外，宿主还认一种自己的插件包容器：PBClus，扩展名 .pbclus。当前格式是 v2：写出时用 v2，读取支持 v1~v2。 权威实现是 backend/pkg/plugin/pbclus/（pbclus.go、 pbclus_platform.go、pbclus_sign.go）。 这一节讲「是什么、为什么这么设计、怎么用」；字段偏移、校验顺序这类实现细节见 PBClus-格式规范.md。

v2 相对 v1 增加了两大能力：多平台包（一个包带多个平台的二进制）与 可选签名。

💡 为什么必须升版本，而不是「加个可选字段」

v1 的解析方不认识平台字段。把多平台包硬塞给 v1 解析方，它会把所有平台的二进制 解到同一个路径上，最后写进去的那个胜出 —— 于是静默装上一个架构不对的二进制， 表现为「插件启用后立刻崩」。升版本让老解析方直接拒绝，而不是做错事。 这正是版本字段存在的意义。

v1 包继续支持：它的条目天然都是通用文件（无平台标签、无签名），v2 的读法能完整覆盖 v1 的语义， 所以不需要保留两套解析逻辑。

为什么不是「zip 改后缀」

改后缀只是换个名字，内容仍然是 zip：解析规则、攻击面、允许的结构全都照旧。 文件名叫 .pbclus 而内容是 zip，等于既没得到新格式， 又让「看到 .pbclus 就知道该怎么处理」这件事变得不可靠。 所以这里定义的是一个真正的容器，把一整类问题在格式层面消灭掉：

问题zip 的做法PBClus 的做法
畸形路径 格式不管，留给每个解压方各防一遍 路径必须规范化、相对、纯正斜杠 —— 打包时就拒绝，解包时再校验一次（两侧调同一个校验函数）
符号链接 / 设备文件 是合法条目；一个 symlink 条目就能让解压结果指向宿主任意文件 格式里不存在这些条目类型：只有普通文件与目录
重复路径 允许同名条目，解压出什么取决于实现顺序 重复条目直接拒绝 —— 唯一性按 (路径, 平台) 判定（v2 起，同一条路径可以有多个平台的版本）
「文件与目录同名」 允许 lib 与 lib/x.so 共存，结果同样取决于顺序 前缀冲突直接拒绝
损坏定位 整体解一遍才知道坏没坏 头部带清单/载荷摘要，尾部带整文件摘要与总长，每个条目还有自己的 SHA-256 —— 能说出是哪个文件坏了
「这到底是什么」 靠扩展名猜，改名就骗过去了 靠魔术字识别：把 zip 改名成 .pbclus 会被识别为 zip 并明确报错

文件布局

┌──────────────┬─────────────────┬───────────┬───────────────┬─────────────┐
│ Header 128 B │ Manifest (JSON) │ Payload   │ Signature ?   │ Footer 48 B │
└──────────────┴─────────────────┴───────────┴───────────────┴─────────────┘
Signature 只有头部 flags 的 FlagSigned 位置位时才存在，恒为 108 B
全部整数小端（little-endian）

清单紧随头部，载荷紧随清单，签名块（若有）紧随载荷，尾部固定在文件末尾。 载荷是各条目压缩后字节的顺序拼接，每个条目在清单里记录自己的 offset 与 packedSize；条目必须紧密排列，不允许空洞或重叠。 

manifestOff == 128
payloadOff  == manifestOff + manifestLen
contentEnd  == payloadOff + payloadLen
contentEnd + 签名块(0 或 108) + 48 == 文件实际长度

contentEnd 是「头部 + 清单 + 载荷」的结束偏移。它同时是整文件摘要与签名 覆盖范围的右边界 —— 签名块自己不在被签内容里（含签名本身，算进去就自指了）。

82version写出时是 2。读取方接受 1~2；更高版本必须直接拒绝（它可能带了本程序不认识的平台标签或签名，硬读会装错二进制），也不做「向后兼容猜测」

偏移长度字段说明

signed与头部 FlagSigned 位必须一致。两处说法不一致说明文件被拼过，直接拒绝
💡 条目按 (path, platform) 排序后写入

同样的输入产生同样的字节布局，便于比对与复现。平台参与排序键，所以多平台包里同一路径的 多个版本会相邻，出问题时一眼能看出「这个文件有哪几个平台」。 另外「用了 deflate」不是必然：压缩后反而更大的条目会回退成原样存 （打一个已经压过的 .exe 时 DEFLATE 经常略微变大，硬压只会让包更大更慢）。

校验边界：完整性、签名有效、受信任是三件不同的事

🚫 这三件事必须分开说，混起来就等于没做校验
状态它证明了什么它不证明什么
完整性（校验通过）内容没被意外损坏、没被截断内容没被人动过 —— 攻击者改完内容可以把所有摘要同步改一遍
签名有效（Valid）内容与签名自洽签名者是谁、你要不要信任它
已受信任（Trusted）签名者的 keyId 在宿主信任库里签名者以后不会做坏事（信任是信任，不是保证）

容器里的 CRC-32 与 SHA-256 只保证完整性：它们是公开可算的校验和， 不提供任何防伪能力。攻击者改完一个包的内容，可以把头部 CRC、清单摘要、 载荷摘要、逐条目摘要、尾部 fileSHA 全部同步重算一遍 —— 此时 Verify() 会通过，只有签名会失败（TestSignatureCatchesWhatIntegrityCannot 构造的就是这个场景）。所以「完整性检查通过」在任何时候都不能被当成「内容没被人动过」。

签名能抓住上面那件事，但「签名有效」也不等于可信：公钥内嵌在包里， 任何人都能签一个验证通过的包。安全语义完全来自宿主的信任库，只有「已受信任」才算数 —— 详见 10.3。

所以装插件时要把包当成不可信输入：校验告诉你「这个包完整不完整」， 签名告诉你「内容与签名是否自洽」，只有信任库才能告诉你「这是不是你想装的那个人发的」。 文档里不制造「校验通过 = 安全」的错觉。

路径规则

打包与解包两侧共用同一个校验函数，避免两套规则漂移。逐条如下：

  • 非空，且长度 ≤ 512 字节（按字节算，不是字符数）；
  • 只允许正斜杠。反斜杠一律拒绝 —— 否则在 Windows 上它会被解释成分隔符，让「路径合法」变成一件平台相关的事；
  • 必须是相对路径：不以 / 开头，不含冒号（挡盘符与 NTFS 数据流）；
  • 不含 NUL 与控制字符（< 0x20 或 0x7F）；
  • 逐个路径段检查：. 与 .. 段直接点出来拒绝，空路径段（a//b、结尾 /）同样拒绝；
  • 每个路径段都不得是 Windows 保留设备名（CON / PRN / AUX / NUL / COM1…COM9 / LPT1…LPT9，大小写不敏感）。比较的是第一个点之前的部分，所以 con.txt 一样被拒；
  • 最后用「规范化后必须等于原串」兜底。

检查顺序是刻意的：把 a/../x 报成「含 .. 路径段」比报成 「应写成 x」有用得多 —— 后者等于把一次目录穿越轻描淡写成格式问题。 

../escape.txt        # 父目录穿越
a/b/../../../x.txt   # 深层穿越
/etc/passwd          # 绝对路径
C:/x                 # 盘符冒号
..\..\x.txt          # 反斜杠
a//b.txt             # 空路径段
./a.txt              # . 路径段
dir/COM1.txt         # Windows 保留设备名

解包安全：两道独立防线

只靠路径规则不够 —— 规则是「对字符串的白名单检查」，真正决定文件落在哪的是 把路径拼成绝对路径之后的结果。所以宿主做两道：

1. 格式路径规则

每个条目路径先过校验函数。挡的是畸形写法：目录穿越、绝对路径、反斜杠、保留设备名。

2. 解析后的前缀校验

拼出绝对目标路径后，再检查它确实落在目标目录之内。挡的是「规则想漏了」的情况。

✅ 这两层都是承重的，不是装饰

作者用「结构完全合法、摘要全部正确、但清单恶意」的容器反向验证过： 把两层同时停用，目录穿越就会成功。也就是说单独拿掉任何一层都会留下缺口 —— 这不是「多写一层保险」，而是两件必须同时成立的事。

另外，解包时每个条目写出都会校验声明长度与内容摘要，任一不符立即失败并删掉写了一半的文件 —— 半损坏的插件目录比直接失败更难排查。读取侧还有每个条目 64MB + 1 字节的硬上限， 即使清单里的 size 撒谎也撑不破，这是防解压炸弹的关键一环。

安装顺序（顺序本身是设计的一部分）

  1. 解析结构魔术字、版本、头部 CRC、清单摘要、尾部魔术字与总长、长度不变量。老版本或更高版本在这一步就被拒。
  2. 整体校验载荷摘要、整文件摘要、逐条目摘要。损坏的包在这里说清「坏在哪」，而不是解到一半失败留下半成品目录。
  3. 平台检查用清单里的 platforms 判断 supports(当前平台)。必须在解包之前 —— 顺序错了，错误信息会变成「入口文件不存在」，与本平台的插件目录问题混在一起，排查方向完全跑偏。
  4. 签名策略按 plugin.signatureMode 判定，只认「已受信任」（见 10.3）。
  5. 解包只解通用条目 + 当前平台条目，其它平台跳过并计入 skipped。
  6. 走既有安装流程清单解析、插件名检查、entry 存在性校验、复制、落库 —— 与 zip 那条路完全一致，不会出现两套安装语义。
💡 平台检查在解包之前，而不是解到一半才发现

不支持当前平台时，安装器给的是能照着做的错误： 「这个插件包不支持当前平台：包内含 linux/amd64，当前是 windows/amd64。 用 pbclus-pack pack --targets windows/amd64,linux/amd64 重新打包即可做成跨平台包」。 说清「包支持什么、当前是什么、怎么办」三件事，而不是只说「不支持」。

怎么给参数结果
--targets a,b多平台包：各平台文件取自 dist/<goos>-<goarch>/，根部其它文件为通用。不加 --build 时会先检查每个平台目录里确实有入口（按目标平台的语义找，Linux 上打 Windows 包就找 foo.exe），缺一个就报错
--targets a,b --build用 go build 把各平台入口交叉编译到临时目录再打包，不写入作者的源码目录（需要源目录有 go.mod；非 Go 插件请自己把产物放进 dist/）

自动判定的规则刻意保守，三条：

  1. 入口不是原生可执行文件（脚本、字节码、数据文件）→ 通用包，清单写 platforms = ["any"]；
  2. 入口是原生可执行文件、且类型与当前主机一致 → 标注当前平台；
  3. 类型与主机不一致 → 报错，要求显式指定（--platform 或 --targets）。
💡 第 3 条为什么不猜

在 Linux 上打一个 Windows 的 .exe，自动标成 linux/amd64 会让一个带着错误 平台信息的包流通出去，装到哪儿都不对。报错的代价只是多打一行参数， 猜错的代价是装上一个跑不起来的二进制 —— 这个交易很划算。

⚠️ 把平台相关的包标成「通用」是最常见的坑

一个只带 Windows 二进制的包如果标成通用，装到 Linux 上会以「入口文件不存在」失败 —— 一个与真实原因（平台不匹配）相距很远的错误信息。pack 在单平台包里发现 「只有 foo.exe、没有 foo」时会额外提示：清单里的 entry 不带后缀是对的 （宿主在 Windows 上会自动补 .exe），但在 Linux/macOS 上宿主会找 foo 并失败； 要跨平台分发，请用 --targets 打一个多平台包。

.git  .svn  .hg  node_modules  __pycache__
.DS_Store  Thumbs.db  desktop.ini
*.pbclus  *.zip  *.log  *.tmp  *.swp  *.bak  *~

另外 pack 会先按与宿主同一套规则检查 plugin.json， 清单有问题当场报错，不用等装的时候才发现。源目录里的符号链接与设备文件会被跳过而不是打进去 —— 格式里根本不存在这类条目。

10.2 多平台包

带原生二进制的插件本来就是平台相关的，而作者通常只想发一个文件。 v2 的答案是一个包里同时装多个平台的二进制，安装器按当前平台只解出需要的那一份。

平台标签

格式是 <goos>/<goarch>，与 Go 的 GOOS/GOARCH 一一对应，也与 Docker 的写法一致，不需要额外解释：linux/amd64、 windows/amd64、darwin/arm64……

校验只检查形状（两段、小写字母数字下划线点、长度有限）， 不做「合法 GOOS 白名单」：白名单会让格式随 Go 版本更新而失效 —— Go 每新增一个 GOOS，老解析方就会拒绝新包。形状校验挡住的是注入与拼写错误， 那才是这里的职责。

💡 磁盘上用短横线，清单里用斜杠

目录名里不能有斜杠，所以源码目录的约定是 dist/linux-amd64/； 清单与条目里的 platform / platforms 一律写 linux/amd64。

清单怎么表达

位置字段语义
清单顶层platforms["any"] = 通用包（v1 包与纯脚本插件都属于此类）；否则是具体平台列表，如 ["linux/amd64","windows/amd64"]。两种不能混用，也不能声明了某平台却一条该平台的条目都没有
每个条目platform可省略。空 = 通用（任何平台都解出来：plugin.json、脚本、素材）；否则只给该平台，且该平台必须在顶层 platforms 里

于是同一条路径可以有多份不同平台的条目（myplugin 在三个平台目录里各有一份）。 唯一性因此按 (路径, 平台) 判定，而不是按路径 —— 同一平台下同名条目出现两次仍然拒绝， 那会让解包结果取决于顺序。条目排序也带上平台，同一路径的多个版本在清单里相邻。

声明式清单有一个直接好处：不下载、不解包也能判断兼容性。 安装器据此在解包之前就拒绝不匹配的包，给出的是「包内含 X、当前是 Y、用 --targets 重新打包」这种能照着做的错误 —— 而不是解到一半说「入口文件不存在」，让人以为打包漏了文件。 这个顺序是有意的：把「平台不匹配」报成「入口文件不存在」， 等于把管理员引向一个跟真实原因无关的方向。

源码目录约定

myplugin/
├── plugin.json                # 通用条目（根部其它文件也都是通用）
├── lib/helper.py              # 通用条目
└── dist/                      # 各平台专属文件的约定位置，自己不打进包
    ├── linux-amd64/myplugin
    ├── windows-amd64/myplugin.exe
    └── darwin-arm64/myplugin

多平台模式下 dist/ 之下的文件按子目录名归属平台，其余文件是通用条目。 dist/ 本身不作为通用目录打进去。 源目录里存在 dist/<goos>-<goarch>/ 布局而你没声明平台时， 打包器会直接报错而不是静默忽略 —— 静默忽略会打出一个「只含 plugin.json 的包」， 装上去必然失败。

解包时发生什么

只解「通用条目 + 当前平台条目」，其它平台的条目跳过而不是报错： 一个包装了三个平台、在其中一个平台上只用得上其一，这是正常情况而不是异常。 跳过的数量会在解包结果与安装结果的 skipped 里如实报出来 —— 管理员看到「包里还有 6 个别的平台的文件被跳过」才不会困惑。

10.3 签名与信任

v2 增加了可选签名块：定长 108 字节，位置在载荷之后、尾部之前。 有没有签名由头部 flags 的 FlagSigned 位决定。定长是刻意的：Ed25519 的签名恒为 64 字节、公钥恒为 32 字节，所以「有没有签名」只需要一个位， 不必在头部再开一个长度字段（那会让头部布局为签名而改动）。布局见上面的 Signature（108 字节）表。

keyId 必须与内嵌公钥自洽（keyId == hex(SHA-256(公钥)[0:8])），否则拒绝： 不一致意味着「这个包是谁签的」有两处互相矛盾的说法，攻击者可以把一个可信 keyId 贴到自己的公钥前面来冒充。

签名覆盖什么

签名消息 = "PBClus/v2 signed-package\n" ‖ fileSHA
fileSHA  = SHA-256(Header ‖ Manifest ‖ Payload)     # 就是尾部里那个值
  • 前缀是域分隔：保证这个签名不会被挪用到别的协议里去。
  • 签名块自己不在被签内容里（它含签名本身，算进去就自指了）。所以 fileSHA 的右边界是 contentEnd（头部 + 清单 + 载荷的结束偏移）， 不是「文件末尾 − 48」。
  • 长度不变量：contentEnd + 签名块(0 或 108) + 48 == 文件大小。
🚫 最重要的一段：内嵌公钥意味着「任何人都能签一个验证通过的包」

公钥是内嵌在包里的。任何人都可以用自己的密钥签一个包，再把对应公钥一起放进去 —— 这个包会「签名有效」。所以必须把三件事分清楚：

  • 「签名有效」（Valid）只证明内容与签名自洽，不证明签名者是谁，也不证明你要信任它。
  • 安全语义完全来自宿主的信任库（keyId 白名单）。只有「已受信任」才算数， 安装决策只能用「已受信任」。
  • 宿主没有信任库时不会信任任何签名 —— 不会退化成「信任所有签名」。空信任库 ≠ 信任所有签名。
  • 内嵌公钥不是多余的：它让信任能够被建立（管理员第一次信任某发布者时可以比对 keyId）， 也让「这个包是谁签的」可被审计。

签名能抓住完整性检查抓不住的东西

格式里所有摘要与 CRC 都是公开可算的。攻击者改完内容，可以把头部 CRC、 清单 SHA-256、载荷 SHA-256、逐条目 SHA-256、尾部 fileSHA 全部同步重算一遍 —— 此时 Verify() 会通过，只有签名会失败。 （实现里的 TestSignatureCatchesWhatIntegrityCannot 构造的就是这个场景。）

💡 这就是「为什么需要签名」的最有力说明

摘要防的是「意外损坏与截断」，防不住「有人照着算法重新算一遍」。 所以「完整性检查通过」这句话，在任何时候都不能被当成「内容没被人动过」。 签名是唯一能区分这两件事的东西 —— 前提是签名者的 keyId 在你的信任库里。

签名策略

策略行为
off完全不看签名
warn 默认照装，但把签名状态写进安装结果的 warnings，界面必须如实展示风险
require只接受受信任签名。无签名、签名无效、签名有效但未受信任，三种情况都拒绝安装

配置项在 conf 的 plugin.signatureMode。 默认是 warn 而不是 require：require 会让所有存量无签名插件在升级后 立刻装不上，而建立信任库需要管理员先操作一步。需要严格的环境把它设成 require 即可，那时不存在降级空间。

⚠️ 策略值写错时按 require 处理

写错的值（比如 strict）不会被当成 warn 或 off， 而是按最严格的 require 处理（fail closed）。配置笔误不该悄悄降低安全门槛。

信任库

宿主数据目录下的 plugin-trust.json：

{
  "keys": [
    {
      "keyId": "3f2a9c1d4b6e7081",
      "name": "某发布者",
      "publicKey": "<base64 的 32 字节 Ed25519 公钥>",
      "addedAt": "2026-10-07T05:51:00Z"
    }
  ]
}
  • 填了 publicKey 就必须与 keyId 自洽：否则会出现「信任库里写着可信的 keyId、 公钥却是别人的」，等于信任了一个假发布者。所以推荐填公钥 —— 只写 keyId 无法防止这种替换。
  • 文件不存在 = 空信任库（空库 ≠ 信任所有签名），这不是错误，省掉了「必须先建一个文件」的步骤。
  • 文件存在但非法 = 报错，不会被静默当成空库：静默降级会让「我明明配了信任库」 变成一个查不出原因的问题。
  • 用 pbclus-pack trust add 维护它，然后把文件放到宿主的数据目录下即可生效。
