插件运行时、进程外通信与生命周期

NebulaDrive 插件系统完全指南（平台 v2）

对应代码：backend/pkg/plugin/（协议 + 契约 + 钩子表 + 注册表 + 宿主 + 安装器）、 backend/pkg/pluginset/（启动接线）、backend/controllers/plugin_ext.go（扩展点控制器）、 backend/internal/pluginhttp/（插件 HTTP 页面反代） 本文所有结论均从源码逐行核对得出，不是设计文档。凡与代码不符之处，以代码为准。

插件制作向的手把手教程见 docs/插件制作指南.html 与 docs/plugin-wiki/； 本文是架构与机制向的完整参考。

0. 平台 v2 现状

插件以独立子进程运行，通过 stdin/stdout 上的 JSON-RPC 2.0 与宿主通信。 启用 = 拉起进程，禁用 = 杀进程，主服务不重启。

能力 状态
协议版本 v2（ProtocolVersion = 2），兼容 v1 插件零改动
钩子 99 个，分 18 组，全部真接线（hooks_wiring 由测试静态校验，无装饰性占位）
三档能力 通知（Emit）/ 决策（Decide、Gate）/ 变换（Mutate、CtxPatch）
注册型扩展点 12 类：storage/auth/notify/preview/payment/contentScan/backup/restore/cli/search/theme/page
多语言运行时 php / python / node / go / binary / external（宿主只做 LookPath 探测，不内置解释器）
插件自建 HTTP 页面 宿主分配端口并反代 /ext/<plugin>/*
前端 UI 扩展 动态侧边栏、iframe 插件页、主题 CSS 变量、插件设置面板
双层默认关闭 全局总开关默认 false + 单插件安装后默认 disabled
进程内 Go 插件 ✅ 仍支持（plugin.Register）
WASM / .so 动态库 ❌ 有意不做（WASM 需 CGO；plugin.Open 在 Windows 编译不了）

双层默认关闭（安全设计，不是没做完）

  1. 全局总开关默认 false：后台开启时必须显式 acknowledge=true —— 插件可注册 HTTP 页面且 /ext/* 完全透传鉴权，等同交出服务器执行权限；
  2. 单插件安装后默认 disabled：必须显式启用（启用前还要过插件协议关卡）。

冒烟脚本与 CI 都按这两层走（先开总开关再启用插件）。

为什么是子进程，而不是 plugin.Open

Go 原生 plugin.Open 只支持 Linux/macOS 且需要 cgo——Windows 编译不了； 即便可行，还要求工具链与依赖版本严格一致。WASM（wasmtime-go）需要 CGO。 子进程方案：跨平台、语言无关、崩溃隔离、真正的热插拔。

1. 插件契约：v1 与 v2

v1 契约（继续完全支持）

myplugin/
├── plugin.json     ← 清单（name/entry/protocolVersion/hooks 必需）
└── myplugin        ← 可执行文件（Windows 自动补 .exe）

v1 插件按 protocolVersion: 1 声明，宿主握手时按插件声明的版本呈现协议， 零改动兼容。现有的 7 个示例插件全部是 v1 契约。

v2 三文件契约

myplugin/
├── plugin.json     ← 元数据
├── register.go     ← 纯声明（go/parser 只读 AST，不编译不执行）
└── co.BEGG         ← JSON：runtime、解释器要求、主页、listen、UI 扩展点
  • register.go 用 Go 语法声明版本、安装内容、hooks、providers—— 但它不会被编译执行，只被解析。这让人能在一个文件里看清插件要什么；
  • co.BEGG 声明运行方式：runtime 可为 php | python | node | go | binary | external， 可要求解释器版本（如 php>=8.1）；
  • 解释器探测：缺运行时在装载阶段直接报错，宿主不静默降级—— 装了一个 PHP 插件却没装 PHP，报错会说清楚，而不是插件莫名不工作；
  • 三个文件递归定位，register.go/co.BEGG 相对路径以自身所在目录为基准—— 塞一层子目录也能识别。
  • 诊断：GET /api/admin/plugins/contract/:name 返回三文件缺失/解析结果， 后台"契约诊断"面板直接展示。

v2 与 v1 的清单一致性有校验：register.go 声明的 ProtocolVersion 与 plugin.json 的 protocolVersion 不一致会被拒绝。

2. 钩子体系：99 个、18 组、三种能力

与 v1 的兼容承诺

v1 冻结的 10 个钩子名（onEmail/onBackup/onRestore/onApiAuth/ onDBMigrate/onRateLimit/onAntiLeech/onCLI/onCollabOpen/onCollabSave） 永久保留、语义不变，表中 Since: 1。存量插件不会因升级失效。

三档能力（HookMeta 的 Blockable/Mutatable 决定）

档 语义 典型钩子
通知 Emit 派发即忘，结果不读 onEmail、onBackup、onDBMigrate
决策 Decide/Gate 返回 blocked 即拦截 onAntiLeech、onApiAuth、onShareDownloadBefore
变换 Mutate/CtxPatch 插件回写 ctx 改变业务行为（进程内外均生效） onCollabOpen（写 url 则 302）

业务侧统一经 internal/hooks 的 Emit / Decide / Mutate / Gate 调用； FireIf 在无订阅者时短路——没装插件的部署零派发成本。

分组（18 组，前端按组展示）

system / request / auth / user / file / content / share / task / webdav / storage / collab / notify / billing / audit / backup / api / plugin / limit。

完整钩子表见 pkg/plugin/hooks_table.go（唯一事实来源），或管理端 「插件 → 钩子」页（数据来自 ListPluginHooks，含真实 handler 计数）。

v1 语义锚点（升级不破坏的守卫）

TestV1FrozenHooksPreserved 静态守住：10 个冻结钩子名字/Since=1/Wired、 onAntiLeech 与 onApiAuth 必须 sync+blockable、 onShareDownloadBefore（v2 补上的分享下载闸）必须可拦截。

3. 注册型扩展点（12 类 Provider）

钩子是事件，扩展点是能力替换——插件声明"我来提供 storage"，宿主 就会把存储调用路由给它。

// pkg/plugin/registry.go
ProviderStorage / ProviderAuth / ProviderNotify / ProviderPreview /
ProviderPayment / ProviderContentScan / ProviderBackup / ProviderRestore /
ProviderCLI / ProviderSearch / ProviderTheme / ProviderPage
  • 声明处：register.go（providers 列表）；
  • 调用处：internal/hooks.Call(kind, name, ctx)；
  • 管理端「UI 扩展点」面板可看每个插件声明了哪些能力。

例：POST /api/admin/backup 触发注册型 backup 插件导出数据（controllers.Backup）； 宿主自己的系统备份在 /api/admin/system/backup（生成 zip，见 §6）—— 两者是不同的东西，路径刻意分开。

4. 插件 HTTP 页面与 UI 扩展

  • 插件可自起 HTTP 服务，宿主分配端口并反代 /ext/<plugin>/*；
  • /ext/* 的鉴权完全透传给插件——插件自负责（这也是双层默认关闭的原因之一）；
  • 前端：动态侧边栏（主界面/后台/移动抽屉）、iframe 插件页容器、 主题 CSS 变量覆盖（PluginThemePicker）、插件设置面板（PluginSettingsPanel）；
  • 0.0.0.0 归一：后台绑定域名用域名、绑定 IP 用 IP、都没绑默认 127.0.0.1。

5. 安装：zip / PBClus / 信任

安装器按魔术字识别包格式（不看扩展名）：

格式 识别 说明
zip PK\x03\x04 历史格式，继续支持；zip slip/bomb 三重限额
PBClus PBClus\x1a\x0a 本项目的容器格式；把 zip 改名成 .pbclus 会被明确拒绝

PBClus 要点（完整规范见 docs/PBClus-格式规范.md）

  • 多平台：条目带 platform（goos/goarch），清单声明 platforms； 解包只取「通用 + 当前平台」，其余跳过并如实计数；
  • Ed25519 签名：可选签名块；签名有效 ≠ 可信——公钥内嵌在包里， 任何人都能签出"有效"的包，安全决策只认信任库（keyId 白名单）；
  • 签名策略 off / warn（默认）/ require，配置值写错按 require（fail closed）；
  • 打包工具 pbclus-pack（pack/inspect/verify/unpack/keygen/trust）；
  • 管理端「签名与信任」页可加/移除公钥、改策略。

安装安全（宿主替你做的）

zip slip 每条目前缀校验、解压总量 256MB/单文件 64MB/条目 2000 三重限额、 拒绝符号链接、Windows 保留名拦截、entry 禁止路径分隔符、 卸载需二次确认密码。

6. 系统备份 / 恢复（与插件备份扩展点并存）

路由 语义
POST /api/admin/system/backup 宿主自己生成 zip（SQLite 库 + manifest.json），触发 onBackup 钩子
GET /api/admin/system/backup/download 下载备份包（双防线挡路径穿越）
POST /api/admin/system/backup/restore 暂存制恢复：校验 SQLite 文件头 → data/restore/ + PENDING，下次启动在 db.Init 之前应用（热替换运行中的库会损坏数据）
POST /api/admin/backup v2 注册型 backup 插件扩展点

恢复提交时触发 onRestore（异步通知，拦不住——需要否决在权限层解决）。

7. 插件命令行（onCLI）

nebula plugin <cmd> [args...]：初始化依赖 → 派发 onCLI → 退出， 不启动 HTTP 服务。

  • 插件往 ctx 写 cliOutput（打印）与 cliExitCode；
  • 退出码约定：0 成功 / 1 用法错误或被插件拒绝 / 2 未安装；
  • 7 个示例插件都实现了同名自检命令。

10. 常见陷阱

进程内 handler 的坑（进程外插件由宿主隔离，panic 不炸宿主）：

  1. handler panic 要自己 recover——Fire 不兜，炸的是整个请求；
  2. ctx 数字经 JSON 往返是 float64——断言 int/uint 会静默失败 （写一个兼容 int/uint/int64/float64 的取值函数）；
  3. 不要在 handler 里 Register——锁不可重入，死锁；
  4. ctx 是同一个 map——后续 handler 能看见你的修改，也会被篡改；
  5. 拦截只认 IsBlockedError（error 文本含小写 blocked）—— ctxPatch:{"blocked":true} 无效，判定语义只此一处；
  6. onDBMigrate 每次启动都触发——建表必须 CREATE TABLE IF NOT EXISTS；
  7. 插件系统默认双层关闭——总开关没开时一切 503，先看后台开关；
  8. 安装后要启用——安装不自动启用（协议关卡在后端强制）；
  9. 首次安装后要重启服务——bootstrap 只在启动时跑，不重启宿主为 nil；
  10. 配置改完要重启插件——配置在启用时下发；
  11. 失败路径的 onApiAuth 与成功路径语义不同——前者提供新凭据方式 （无 Authorization 的 HMAC），后者否决/补充有效令牌，别混用。

11. 写文档时的诚实边界

  • permissions 声明不强制，只展示给管理员；
  • 商店条目的 version/author 不可信，以安装后磁盘上的 plugin.json 为准；
  • 签名有效 ≠ 可信（公钥内嵌，任何人可签；信任决策只看 TrustStore）；
  • 插件沙箱不存在——隔离靠进程边界 + 权限自觉；
  • /ext/* 鉴权完全透传给插件；
  • openInNewWindow 之类的前端诉求宿主做不到（固定 302）——不做假承诺。
