NebulaDrive 不足总结与改进建议

评估对象：github.com/mrc-sk/nebula-drive，main @ 11d5621（2026-10-05） 评估时间：2026-11-04 评估方式：完整克隆仓库 → 逐文件核查源码与自带文档 → 本地实跑 go build / go vet / go test → 比对 GitHub 元数据与前端依赖公开漏洞库 视角：站长（运营/合规/成本） + 技术评审（架构/安全/工程） 标注说明：【实测】= 我本地跑出来的结果；【代码核查】= 逐行/全库搜索确认；【文档自述】= 项目自己的 CHANGELOG / CODE_REVIEW 已承认的问题

0. 一句话结论

这是一个工程能力明显在线、但产品化与运营化几乎为零的单人项目：存储抽象、引用计数、配置加密的设计水平高于同类国产自托管项目，作者还写了 743 行安全自审并真的修掉了大部分 P0；但它目前的完成度是「能跑起来的功能原型」，不是「可以承载真实用户数据的网盘服务」。

  • 站长视角最致命的不是 bug，而是合规裸奔 + 无备份 + 无社区：公开分享、BT/磁力离线下载、举报/审核/日志留存全缺。
  • 技术视角最刺眼的是「README 写了但代码没有」：三个统计图表接口后端根本不存在；go test ./... 在我这里并不全绿，而文档宣称全绿。

建议定位：自用 / 学习 / 内网试验可以上手；对外提供服务前必须完成第 4 节 P0 清单。

这个失败点与「畸形存储策略 JSON 不得静默回落到 uploads/ 相对目录」有关，属于数据落盘正确性的安全断言。filesystem.New 在解析失败时会回退到 confUploadPath()，在测试环境下该函数返回了非空值，导致断言失败——无论根因是全局 conf 状态污染还是回退条件过宽，结论一致：当前 main 分支不是全绿。 而 CHANGELOG V26-10.0-d 与 CODE_REVIEW.md §6 都白纸黑字写着「go test ./... 全包通过 / EXIT=0」。文档与实物不符，且发行门禁没有拦住它。

2. 站长视角：不足与建议

2.1 合规与法律风险 —— 最高优先级

【代码核查】 全库搜索 report / 举报 / 审核 / 敏感词 / moderation / hash 黑名单 零命中。也就是说：

  • 有公开分享（提取码 + 密码 + 5 分钟签名 URL）、有离线下载（HTTP / BT / 磁力）、有用户注册与套餐付费，但没有内容审核、没有举报入口、没有侵权投诉通道、没有操作日志留存策略。
  • 这正好构成典型的违规内容传播链路。国内运营涉及 ICP 备案与公安备案、《网络安全法》日志留存（≥6 个月）、《个人信息保护法》、以及著作权的「通知—删除」义务。BT/磁力下载尤其危险，站长很难主张自己只是技术中立。

建议（上线前必做） 1. 后台加「举报/投诉」入口 + 工单处理流程 + 处理时限，分享页放免责声明与投诉邮箱。 2. 访问/上传/分享/下载日志结构化落盘并保留 ≥6 个月，支持按文件与按用户追溯。 3. 默认关闭 BT/磁力离线下载，或仅限管理员 + 明确风险提示；HTTP 离线下载保留出站白名单（代码已有 internal/service/outbound.go，可复用）。 4. 分享文件做哈希黑名单 + 可选接入内容安全 API；对公开分享设有效期、次数上限与下载限速。 5. 若提供付费套餐/兑换码，补齐用户协议、隐私政策、退款与发票流程。

2.2 AGPL-3.0 是站长的真实义务，不是一句「开源协议」

【文档自述】 README 与 AGPL_通俗说明.md 已经写清楚：改过代码并部署到公网供他人使用，必须向这些使用者提供完整对应源码（§13），二进制分发也要随附源码或书面要约。

  • 只要站长做过二开（换 Logo、接短信、改套餐逻辑都算），对外服务就要公开改动源码。
  • 想做闭源商业 SaaS 或给客户做闭源定制，需要双授权（当前单一版权人，操作上可行，但要提前决定）。
  • 插件分发同样受约束；仓库里已有「插件协议要求 AGPL 合规」的设计，方向是对的。

建议：现在就明确「自用 / 对外服务 / 商业化」三种定位各走哪条路；对外部署时准备一个可下载的对应源码包（含 commit hash 与构建脚本），别等被质疑才补。

2.3 数据安全与业务连续性

【代码核查】 无内置备份/恢复实现（只有 onBackup / onRestore 插件钩子占位），无恢复演练文档，无 RPO/RTO 说明。

  • 默认 SQLite 单文件 + 加密密钥同在 data/ 目录：一次误删、磁盘损坏或密钥丢失 = 全站数据没了。
  • 单实例设计（README 已诚实列出）：WebDAV 锁、登录失败计数、验证码阈值、限流、分片上传会话全在进程内存，重启即丢；分片断点续传状态至今仍在内存 map（file.go 的 chunkUploads），只加了 24h 清理，【文档自述】 CHANGELOG 的已知 Bug #1「落盘到 chunk_sessions 表」仍未实现。
  • 回收站 30 天自动清理、版本只保留最近 10 版 —— 用户误删的兜底窗口比主流网盘短。
  • 迁移到 MySQL/PG 的能力有，但只有 1 个 release、CHANGELOG 自己承认有 4 个版本未补记条目，升级路径缺少可追溯的变更史。

建议：定时快照 + 异地备份 + 每季度一次真实恢复演练；把 data/ 整体纳入备份并单独安全保管 secret.key；生产改用 MySQL/PG 并写清版本升级/回滚步骤；把「分片会话落盘」提到 P1。

2.4 可观测性与运维

【代码核查】 无 /healthz、无 Prometheus metrics、无结构化日志（全库标准库 log.Printf）、无告警、无优雅关闭（watchSignals 只负责回收插件子进程）。start.bat 是前台运行、日志打控制台。

建议：补 /healthz + readiness、结构化日志（含 request id）、错误上报、磁盘水位/流量/登录失败告警；提供 systemd unit（仓库里有 nebuladrive.service，但缺 Docker 镜像，见 3.2）与容器化部署文档。

2.5 项目可持续性：单点维护风险

3 star / 0 fork / 0 issue / 单贡献者 / 停更 30 天 / 仅 1 个 release，且 【代码核查】 没有 SECURITY.md、没有 CONTRIBUTING.md、没有行为准则、没有版本支持策略。

  • 漏洞往哪报？哪些版本会收安全补丁？作者停更后谁修？——三个问题目前都没有答案。
  • 0 issue 不代表没 bug，更可能是没有真实用户，所以所有问题都是作者自己发现的（CODE_REVIEW.md 是自审、FIXLOG.md 1310 行是自修记录、.trae-html-share-packages/ 是 AI 编辑器产物且仍被提交进仓库）。

建议：补 SECURITY.md（私下报告邮箱 + 响应时限）、贡献指南、版本支持矩阵；站长自己保留一份可构建的 fork 与离线依赖缓存，避免上游消失后无法出安全补丁。

2.6 宣传与实物落差 —— 直接伤害用户信任

【代码核查】 我在后端全库搜 stats，只找到 migrate_sensitive.go 里一个无关变量；路由表里只有 /api/admin/dashboard。而前端 client.ts 定义了 trafficStats / fileTypeStats / activityStats 三个接口，Dashboard.tsx 里甚至自己写了注释：

} catch {
  // 后端无 API：空数组 → 图表空态
}

也就是说 README 里「📊 数据统计：KPI 卡片 + 流量趋势折线 + 文件类型饼图 + 用户活跃度热力图」中，后三个图表恒为空态（只有 KPI 卡片有真实数据）。【文档自述】 CHANGELOG 早期版本曾记录「热力图走 mock 数据」——现在连假数据都没了，造假问题消失了，但功能依然没实现。

同类落差还有：【文档自述】 V26-10.0-d 亲口承认此前「插件启用/禁用开关是装饰品（Enabled 字段无任何生产代码读取）」「扩展点数量是 Math.random() 生成的随机数」「插件安装是 alert() 占位」「商店拉取失败一律返回空数组」。这些都在 10-05 修好了，但说明「页面看起来完整」和「功能真的可用」之间长期没有校验机制。

建议：README 加一张功能成熟度矩阵（✅ 可用 / 🟡 Beta / 🔵 规划中 / ⚪ 占位），把 CHANGELOG 里 18 条已知 Bug 分级（Blocker / Major / Minor）并置顶；把三个统计接口实现或删除（现在前端在请求 404）。

3. 技术评审视角：不足与建议

3.1 先说做得好的（我独立复核过，不是照抄自评）

  • 引用计数 + FileObject 分离物理对象：UPSERT 自增、唯一键回退、旧数据 backfill，升级路径考虑得很周全，是全项目最扎实的一块。
  • 存储抽象层 filesystem.Handler：7 个方法的接口 + 工厂注册，Local/S3/OSS/COS/SFTP/远程 WebDAV 都接进来了，扩展性是真的。
  • 安全自审并落地：CODE_REVIEW.md 743 行列出的 P0/P1，我逐条查了当前代码——CORS 已收紧为白名单（routers/router.go 的 allowedOrigin）、filesystem/fs.go 有 ErrPathTraversal 与 safeJoin、internal/service/outbound.go 有 loopback/私网 IP 校验、cryptox.TokenHash 让 PAT 只存哈希、internal/service/{quota,outbound}.go 把配额与上传校验收口、WebDAV 的 LOCK/COPY 有了真实实现、两个 CI 工作流都在。作者确实把「校验收口」这条建议做成了结构性修复，这点值得肯定。
  • 单二进制 + go:embed + 一键试用包（-autoport、-open、中文报错提示）对新手部署很友好。

3.2 实测/核查发现的硬问题

# 问题 证据 级别
1 前端依赖 xlsx@^0.18.5 带两个已知高危 CVE CVE-2023-30533（原型污染，CVSS 7.8）、CVE-2024-22363（ReDoS，7.5）。SheetJS 在 npm 上最后一版就是 0.18.5，修复版只从 cdn.sheetjs.com 分发（0.19.3 / 0.20.2+）。网盘会解析用户上传的表格，属于真实攻击面 P0

3 三个统计接口后端不存在 全库 stats 零命中；前端注释自认「后端无 API」；README 却列为已实现功能 P1
4 单实例内存状态，重启丢数据 chunkUploads 仍是内存 map；README 已列 WebDAV 锁/限流/失败计数/分片会话五项；CHANGELOG 已知 Bug #1 未修 P1
5 OAuth2 无 PKCE、授权码并发可重放 全库 code_challenge / PKCE / code_verifier 零命中；自评 P2-5 的 redirect_uri 空数组放行、code Used 非原子判断，不在已修清单里 P1

12 README「Docker / deb / rpm 打包」名不副实 仓库无 Dockerfile，只有 nfpm.yaml（deb/rpm） P2

3.3 架构与可维护性

【代码核查】 大文件集中：file.go 1804 行、webdav.go 1003 行、pkg/plugin/host/manager.go 923 行、plugins.go 816 行；前端 Files.tsx 1390 行、Plugins.tsx 734 行、api/client.ts 643 行。自评 §4.1 已建议拆分 controllers/file|upload|version|tag|trash 与 internal/service，收口做了一部分，拆分没做。

db.Get() 全局单例 + 硬编码策略 ID + 每请求多次查 settings（自评 P2-6 的缓存缺失）仍是隐性技术债。

3.4 测试策略的结构性偏差

34 个测试文件看似不少，但：

  • 全部集中在 middleware / pkg / models / conf 这些好测的部分；controllers 有测试但单包跑 298 秒，CI 每次要等 5 分钟，容易被人绕过。
  • WebDAV 包零测试、internal/service 零测试——而这两个正是 P0 高发区。
  • go test -race 只在 CI 跑；【文档自述】 作者自己写了「本地 Windows 无 MinGW，CGO_ENABLED=0，本地跑不了 race，只有 CI 能验」，意味着本地开发阶段拿不到并发问题反馈。
  • 自评里提的「权限矩阵测试 / WebDAV 集成测试 / SSRF 用例 / 并发 race 测试」四项，目前只在 routers/integration_test.go 有部分覆盖。

3.5 前端健壮性与体验

【代码核查】 16 处 alert() 充当成功/失败提示（后台管理页几乎全靠弹窗）；catch { // ignore } 静默吞错误遍布 Dashboard；ShareList.tsx 明确注释「后端只回 fileId 不回文件名，只能显示占位」；i18n 五语言靠 check_i18n.py 脚本门禁（这个门禁设计是好的）。

建议：统一 Toast/错误边界组件替换 alert；后端在分享列表直接返回文件名；对 404/5xx 做可见提示而不是空图表。

4. 改进路线图（两个视角合并，按投入产出比排序）

P0 — 对外服务前必须完成

  1. 修绿 go test ./...，并确认 GitHub Actions 真的启用且能拦截合并；把 -race + 覆盖率下限设为 PR 门禁。顺手给 filesystem 的 conf 全局状态做测试隔离。
  2. 替换 xlsx@0.18.5：改用 xlsx@https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz，或换 exceljs / 服务端解析；同时限制上传表格体积。
  3. 合规三件套：举报入口 + 通知删除流程 + 日志留存 ≥6 个月；默认关闭 BT/磁力；分享页免责与投诉入口。
  4. 备份与恢复：定时快照 + 异地副本 + 一次真实恢复演练；data/ 与 secret.key 分开保管；写下 RPO/RTO。
  5. 补 SECURITY.md 与私下漏洞报告渠道。

P1 — 稳定化

  1. 分片会话落盘（chunk_sessions 表）；WebDAV 锁 / 限流 / 登录失败计数外置 Redis，向多副本演进。
  2. OAuth2 补 PKCE、授权码用 UPDATE ... WHERE used=false 原子消费、redirect_uris 为空则拒绝授权；PAT 撤销联动 session 黑名单。
  3. 插件加签名/校验和校验 + 权限清单（capabilities）+ 默认关闭第三方安装；安装 URL 增加完整性校验。
  4. 补 WebDAV 集成测试（路径穿越、PUT 覆盖、LOCK/UNLOCK、Depth:1 href、白名单绕过）与插件安装器测试。
