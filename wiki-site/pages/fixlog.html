二、逐项说明

P0-1 路径穿越

根因：所有本地/远端 handler 直接把用户可控名称拼进 filepath.Join(root, name)， path.Clean 在 Windows 下不识别 \，因此 ..\..\windows\win.ini 可逃逸出存储根目录。

修复：新增统一的名称归一化 + 前缀校验函数。

// filesystem/fs.go
var (
    ErrPathTraversal      = errors.New("path traversal detected")
    ErrInvalidObjectName  = errors.New("invalid object name")
)

// SafeLocalPath 把不可信的对象名解析为存储根目录内的绝对路径。
// 任何逃逸尝试都返回 ErrPathTraversal。
func SafeLocalPath(root, name string) (string, error) {
    if strings.TrimSpace(name) == "" {
        return "", ErrInvalidObjectName
    }
    clean := strings.ReplaceAll(name, "\\", "/") // Windows 反斜杠归一化
    clean = strings.TrimLeft(clean, "/")
    if clean == "" {
        return "", ErrInvalidObjectName
    }
    for _, seg := range strings.Split(clean, "/") {
        if seg == "" {
            continue
        }
        if seg == "." || seg == ".." {
            return "", ErrPathTraversal
        }
        if strings.ContainsAny(seg, "\x00") || strings.HasSuffix(seg, ":") {
            return "", ErrInvalidObjectName
        }
    }
    joined := filepath.Join(root, filepath.FromSlash(clean))
    absRoot, err := filepath.Abs(root)
    if err != nil { return "", err }
    absPath, err := filepath.Abs(joined)
    if err != nil { return "", err }
    // 双重保险：解析后的绝对路径必须仍在根内
    if absPath != absRoot && !strings.HasPrefix(absPath, absRoot+string(filepath.Separator)) {
        return "", ErrPathTraversal
    }
    return absPath, nil
}

Local handler 的 Put / Get / GetRange / Delete / Size / Copy 六个方法全部改为 经 SafeLocalPath 取路径；SFTPHandler.remotePath 与 WebDAVRemoteHandler.fullPath 改成返回 (string, error) 并做同样的归一化 + 前缀校验（远端路径额外逐段 url.PathEscape）。

防御层次：段级黑名单（.. / : / NUL）→ 反斜杠归一化 → 绝对路径前缀比对。三层独立成立， 任一层被绕过仍有下一层兜底。

修复：

// 覆盖场景：读新内容 → 写新物理对象 → 改 File 指向 → 释放旧物理对象

    body, mimeType, ext, err := readDAVUpload(c, node.Name)   // 走统一校验链
    ...

新增的 readDAVUpload 是 HTTP 上传校验链在 WebDAV 侧的复用入口：

func readDAVUpload(c *gin.Context, name string) ([]byte, string, string, error) {
    ext := strings.ToLower(path.Ext(name))
    if !service.IsAllowedExtension(ext) {          // ① 扩展名白名单
        return nil, "", "", fmt.Errorf("file type not allowed: %s", ext)
    }
    maxBytes := int64(service.MaxUploadBytes())
    body, err := io.ReadAll(io.LimitReader(c.Request.Body, maxBytes+1))
    if int64(len(body)) > maxBytes {                // ② 体积上限
        return nil, "", "", fmt.Errorf("file too large (limit %d bytes)", maxBytes)
    }
    if service.MagicCheckEnabled() && service.IsImageExt(ext) {
        if err := service.CheckImageMagicErr(body, ext); err != nil {  // ③ 魔术字节
            return nil, "", "", err
        }
    }
    return body, mimeTypeFromExt(ext), ext, nil
}

写入成功后调用 auditDAVWrite 落 audit_logs，audit 的 Detail 字段里带 "channel": "webdav"， 与 HTTP 上传共用同一张表、同一套查询。

配额部分同时把原来「读 storage → 比较 → 事后 UpdateColumn("storage", storage+size)」 替换为 service.AddStorageTx（见 P1-5）。

P0-4 WebDAV LOCK / UNLOCK / COPY / PROPPATCH

根因：case "COPY", "PROPPATCH", "LOCK", "UNLOCK": c.Status(200) —— 对客户端谎报成功。 依赖锁做并发保护的客户端会静默覆盖彼此的数据；COPY 后文件根本不存在。

修复：

  • LOCK：实现进程内排他锁表 davLocks，返回完整 RFC 4918 lockdiscovery 响应体与 Lock-Token / Timeout 头。
  • UNLOCK：校验 Lock-Token 头，确认持锁人匹配后释放，否则 409。
  • 锁生效：PUT / DELETE / MOVE 入口处调用 davCheckLock，目标路径被他人持锁时返回 423 Locked。
  • COPY：真正实现递归复制（davCopyNode），支持目录、拒绝覆盖已存在目标（412）、 复制物理对象后走 storage.Retain 与原子配额。
  • PROPPATCH：不再假成功。按 RFC 4918 §9.2 返回 207 Multi-Status，每个属性标记 403 Forbidden 并附 responsedescription，明确告知客户端本服务不支持写属性。

P1-5 配额 TOCTOU

根因：ensureQuota 是「先 SELECT storage → 在 Go 里比较 → 稍后 UPDATE 累加」。 并发 N 个请求同时通过比较，然后各自累加 → 实际用量可超出额度 N 倍。

修复：internal/service/quota.go 引入把校验与写入合并为单条条件 UPDATE 的实现。

// 核心：把「比较」交给数据库，由 WHERE 条件保证原子性
res := tx.Model(&models.User{}).
    Where("id = ? AND (storage + ?) <= ?", userID, delta, maxStorage).
    UpdateColumn("storage", gorm.Expr("storage + ?", delta))
if res.RowsAffected == 0 {
    return fmt.Errorf("%w: have %d bytes, limit %d bytes (%s), tried to add %d bytes",
        ErrQuotaExceeded, u.Storage, maxStorage, label, delta)
}

RowsAffected == 0 有两种含义（条件不满足 / 用户不存在），代码通过二次查询区分， 不会把「用户不存在」误报成「超额」。

P1-6 分片上传

三个独立问题：

(a) meta.Chunks 在锁外被写 chunkUploadsMu 只保护 map 本身，不保护 meta 的内部字段。 多个分片并发上传时同时写 meta.Chunks[idx] → 并发 map write，Go 运行时直接 panic。

修复：给 chunkUploadMeta 加 mu sync.Mutex，Chunks / ChunksBytes / LastTouched 的读写全部持有 meta.mu。

(b) 会话与临时分片永久泄漏 chunkUploads 只增不减，中断的上传（关闭浏览器、网络断）会一直占着 map 条目和 uploads/chunks/ 下的临时文件。

修复：新增 LastTouched 字段 + chunkGC() 后台协程，每 30 分钟扫描一次， 回收超过 24 小时（chunkSessionTTL）未触碰的会话及其分片文件。

(c) 采信前端声明的文件大小 meta.Size 完全来自 ChunkInit 的请求体。攻击者可声明 1KB 实际传 10GB，绕过配额。

修复：

// ChunkUpload：分片序号必须在 [0, ChunkCount) 内，且单分片不超过 chunkSize + 1MB
if idx < 0 || idx >= meta.ChunkCount { 400 }
if file.Size > maxChunkBytes { 413 }

// 累加真实落盘字节数

P2-2 重复扣减配额

根因：Purge 与 cleanupTrash 都是「先 Delete 行 → 再 addStorage(-Size)」或者反过来的 非原子组合。重复点击 / 并发执行会对同一条记录扣减两次，用户已用容量被扣成负数。

修复：先做条件原子删除，只有真正删掉行的那一次调用才继续记账。

res := db.Get().Unscoped().Where("id = ?", f.ID).Delete(&models.File{})
if res.RowsAffected == 0 {
    // 已被其他路径删除，直接跳过，不重复扣减
    return
}
// 只有走到这里才释放物理对象 + 扣配额

cleanupTrash 同样改为 Where("id = ? AND deleted_at IS NOT NULL") 条件删除。

补充说明：本项目的软删除不释放配额（回收站仍占额度），所以 Purge / cleanupTrash 各扣一次是正确语义，问题只在于缺少幂等保护。

P2-7 敏感字段明文入库

根因：五处敏感字段全部明文存库，其中两处的代码注释还写着"加密"：

字段 内容 原注释
User.TwoFactor TOTP 密钥 // TOTP secret，加密 ❌
Policy.Config 存储配置 JSON（含 SFTP 密码 / OSS / COS 密钥） // JSON 加密 ❌
OAuthApp.ClientSecret OAuth 客户端密钥 无
AccessToken.Token OAuth 访问令牌 无
PersonalAccessToken.Token 个人访问令牌 无

DB 一旦泄露（备份被拖、SQL 注入、管理员账号失守），攻击者可直接： 接管任何已开启 2FA 的账号、以明文密码连接用户的 SFTP 存储、冒用 OAuth/PAT 令牌。

关键判断：两类字段必须用不同方案

这是本次改造最需要想清楚的一点 —— 把所有字段一律加密会引入两个真实故障：

类别 字段 方案 依据
需读回原值 TwoFactor / ClientSecret / Policy.Config AES-256-GCM 可逆加密 TOTP 验证需要 secret；Config 要解析出密码去连接存储
只需比对 AccessToken.Token / PAT.Token SHA-256 单向哈希 令牌创建时展示一次，之后所有场景都只是比对

为什么令牌不能用可逆加密：

  1. AES-GCM 带随机 nonce，每次加密结果都不同 → WHERE token = ? 永远查不到
  2. 相同明文得到不同密文 → uniqueIndex 失效

单向哈希同时解决了这两点，而且安全性更高：哈希是确定性的所以索引和查询照常工作， 而数据库泄露也无法直接冒用令牌（明文和可逆加密都做不到这一点）。

为什么不用 GORM hook

原本打算用 BeforeSave / AfterFind 钩子，但项目里 2FA 的开关代码是：

db.Get().Model(u).Update("two_factor", req.Secret)   // ← 值来自 map，不是 struct 字段

钩子只对 struct 字段生效，这条路径的值根本不经过 struct，钩子拦不住， 会静默写入明文。改用 database/sql 的 driver.Valuer / sql.Scanner 自定义类型 （models.Encrypted），它位于所有写入路径的必经之处。

这个选择是踩坑后确定的：先按 hook 写完，grep 时才发现 auth.go 有两处 Update 用法。

平滑升级：密文带版本前缀

密文形如 enc:v1:<base64>。前缀的作用是区分密文与存量明文：

func Decrypt(s string) (string, error) {
    if s == "" || !IsEncrypted(s) {
        return s, nil        // 无前缀 → 按明文原样返回
    }
    return conf.DecryptString(strings.TrimPrefix(s, prefix))
}

这让"直接上线加密"成为可能 —— 存量数据照常可读（老用户的 2FA 不会失效）， 在后续写入时顺带升级为密文，不需要停机做全量迁移。

models.MigrateSensitiveFields() 负责存量转换：分批 500 条、幂等、失败不阻塞启动， 并在 main.go 的 bootstrap() 中调用（紧跟 storage.BackfillFileObjects()）。

连带必须修的三处

  1. User.TwoFactor 字段长度 64 → 255。TOTP secret 约 32 字符， AES-GCM 加密后（+12 字节 nonce +16 字节 tag）base64 约 80 字符，64 装不下。
  2. OAuth 的 WHERE client_secret = ? 失效（库里现在是密文）。 改为按 client_id 查出记录（Scanner 自动解密）后在内存中比对， 并用 crypto/subtle.ConstantTimeCompare —— 顺带消除了时序攻击面。
  3. testutil.SetupDB 必须 conf.Load()。密钥未加载时 EncryptString 报错， 而 Valuer 是 fail closed 的（加密失败即让整个写操作失败）， 结果会是所有创建 User / Policy 的测试全部报错。让测试也走真实加解密路径。

P1-3 搜索历史清理在 MySQL 报 1093

controllers/search.go 的 SaveSearchHistory：

-- 修复前：MySQL 不允许在 DELETE 的子查询里引用被删除的同一张表 → 错误 1093
DELETE FROM search_histories
WHERE user_id = ? AND id NOT IN (
  SELECT id FROM search_histories WHERE user_id = ? ORDER BY id DESC LIMIT 20
)

这个 bug 有个隐蔽之处：SQLite 允许这种写法，所以本地开发完全不会暴露； 一旦部署到 MySQL/生产环境，每次保存搜索历史都报错。

修复方式改为「先定位第 20 条，再删比它更早的」——无子查询，SQLite / MySQL / PostgreSQL 通用：

var keep models.SearchHistory
if err := db.Get().Where("user_id = ?", u.ID).
    Order("id desc").Offset(19).Limit(1).Find(&keep).Error; err == nil && keep.ID > 0 {
    db.Get().Where("user_id = ? AND id < ?", u.ID, keep.ID).Delete(&models.SearchHistory{})
}

注意用 Find 而非 First：GORM 的 First 会自动追加 ORDER BY id，与显式的 Order("id desc") 语义冲突。 keep.ID > 0 的判断保证记录不足 20 条时不做任何删除（用 NOT IN 空列表会误删全部）。

事务边界的三条原则

改造中最容易犯错的是「什么该放进事务」。这里遵循三条：

1. 物理对象写入不进事务。 h.Put(...) 写的是磁盘/对象存储，数据库回滚管不到它。正确顺序是 「先写物理 → 事务内写 DB/配额 → 事务失败则手动删物理对象」：

if err := h.Put(src, sourceName, size); err != nil { /* 失败即返回，无副作用 */ }

if err := db.Get().Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(&f).Error; err != nil { return err }
    return service.AddStorageTx(tx, u.ID, f.Size)
}); err != nil {
    _ = h.Delete(sourceName)   // 补偿：清理已落盘但无人引用的物理对象
    writeQuotaOrServerError(c, err)
    return
}

2. DDL 不进事务。 models.AutoMigrate() 必须留在事务外 —— MySQL 的 CREATE/ALTER TABLE 会隐式提交 当前事务，把它包进 db.Transaction 只会得到一个「看起来有事务、实际没有」的假象。 Install 里这一条尤其重要，因为它是整个安装流程的第一步。

3. 文件写入不进事务。 conf.Save(cfg) 写的是磁盘配置文件，放在事务提交之后。

Install 的额外处理：幂等化

光有事务还不够。Install 的失败点不止在事务内 —— 事务提交后还有 conf.Save。 如果这一步失败，数据库已经写好了但 installed=false，用户重试时会撞上：

  • createAdmin 撞用户名唯一索引 → 永久卡死，只能手工删库

两个配套修复：

// ① 同名用户已存在时更新，而不是报错。
//    能走到这里说明 conf.IsInstalled() 仍为 false（否则被 InstalledBlock 拦下），
//    即系统处于「上次安装中断」状态，此时更新才是符合安装意图的行为。
err = tx.Where("user_name = ?", a.UserName).First(&existing).Error
if err == nil {
    return tx.Model(&models.User{}).Where("id = ?", existing.ID).Updates(...).Error
}

// ② 默认组逐个确保，而不是「组1在就整体跳过」。
//    原实现：if 组1 不存在 { 建组1; 建组2 } —— 若建组1成功、建组2失败，
//    重试时组1已存在 → 整个 if 跳过 → 组2 永远缺失。
if err := ensureGroup(tx, 1, "default", 10<<30, true, true); err != nil { return err }
return ensureGroup(tx, 2, "admin", -1, true, true)

配合这两点，Install 现在可以在任意中断点安全重试。

顺带清掉的隐患

  • reserveStorage 包装函数已无调用者，删除；所有记账统一走 service.AddStorageTx(tx, ...)
  • 新增两个统一的错误响应helper，把「配额不足」与「服务端故障」区分开：
  • HTTP：writeQuotaOrServerError → 配额 400 / 其他 500
  • WebDAV：writeDAVQuotaOrServerError → 配额 507 Insufficient Storage（RFC 4918）/ 其他 500

这样运维看日志能立刻分辨是「用户超额度」还是「数据库出问题」，而不是清一色 500。

6.1 S-1 改密码不吊销会话（最严重）

ChangePassword 改完密码就 return，不碰 sessions 表。

而会话有效性判定在 middleware/auth.go:40：

db.Get().Where("session_id = ? AND expires_at > ?", claims.SessionID, time.Now()).First(&sess)

只查 session_id + 过期时间，与密码完全解耦。后果：

用户发现账号被入侵 → 改密码 → 攻击者手上的 token 在「记住登录」的 7 天里照常可用。

「我改密码了」这个补救动作对已入侵场景完全无效。项目的单设备登录机制 （登录时 Delete(user_id) 清旧会话）做得不错，但改密码这条路没接上。

修复：新增 revokeAllSessions()，删掉该用户全部会话 + 为当前浏览器签发新 token 并重设 cookie。全删而不是只删其他会话——保留任何旧 token 都等于留后门。 当前浏览器通过新 token 无感续上，前端无需改动（ProfileSettings.tsx 改完只提示 OK）。

配套动作： - 写 AuditLog（action: change_password）——这类操作必须可追溯 - 吊销失败时返回 500 而非 200。不能假装成功——密码已改但旧 token 仍有效， 报个错比给个假成功安全

测试有效性做了变异验证：把 Delete 那行注释掉后重跑， TestChangePasswordRevokesAllSessions 报「实际 4 个 —— 旧会话未吊销」并 FAIL。 若只断言「密码改了」而不查 session，删掉整个吊销逻辑测试照样通过 —— 漏洞仍在。

另加两个反向测试：原密码错误、新密码不达标时都不得吊销会话 （否则可被用来强制把受害者踢下线）。

排查过程中我犯的两个错（都记下来）

  1. 用 503 判断「路由已注册」是错的。InstallGuard 是 r.Use 注册的全局中间件， 未匹配路由也会经过它，所以不存在和不存在的路由在未安装状态下都返回 503。 正确甄别要在已安装状态下做：已注册→401（走鉴权），未注册→404。

15. Linux 分发包：文档教用户执行 stop.sh，但包里没有 stop.sh

日期：2026-10-03（给朋友分发 Linux 版时发现）

怎么发现的

准备把 Linux 包发给朋友之前，逐条核对了「包内文件」与「说明文档里让用户敲的命令」， 发现 试用说明.md 第 30 行写着：

而 start.sh 自己也有两处提到 stop.sh：

echo "  [信息] PID=$PID ，停止服务请执行 ./stop.sh"

但包里只有 start.sh，没有 stop.sh。 朋友按文档操作会直接吃到 ./stop.sh: No such file or directory —— 而且是在他已经开始用之后才发现的那种。

根因：两份打包脚本，只有一份记得这文件

  • packaging/build-release.sh 一直有 cp packaging/start.sh packaging/stop.sh ...
  • packaging/repack.py 只复制了 starter（即 start.sh）

也就是说 repack.py 是一份平行实现，两边各写各的。 写它的时候没对照 build-release.sh 已经处理过的事，于是漏了。 这类「两份实现各写各的」的地方，review 时只能靠逐文件对照， 不能指望「我照着原意写」—— 原意已经被另一份脚本固化了。

修法

  1. repack.py 加 SH_SCRIPTS = ["start.sh", "stop.sh"]，Linux/macOS 包都带上；
  2. .sh 自检从「只查启动脚本」改为遍历包内全部 .sh —— 原来的写法漏掉任何一个脚本都会让用户撞上 bad interpreter；
  3. verify_release.py 加断言：Linux/macOS 包必须含 stop.sh 与 Linux上手说明.md。 这条断言守的是「文档提到的文件必须在包里」 —— 比检查文件数量有意义得多，数量对但缺某个文件的情况正是这次漏的。

顺带：Linux 专属上手说明

跨平台的 试用说明.md 讲了功能，但没讲 Linux 用户真正会卡的点。 新增 packaging/Linux上手说明.md，只补这些（不重复已有内容）：

  • 必须先解压，不能直接跑压缩包
  • chmod +x 的时机 —— 明确说明「包里已带权限，是某些解压工具会丢它」

  • bad interpreter: /bin/sh^M 的真实原因是文件传输中被改坏， 不是脚本写错 —— 避免用户去改脚本

根因与修复

# 问题 根因 修复

为什么预览要单独一个端点

预览与下载的差别不只是响应体：

  • Content-Disposition 必须不同。用 attachment 时浏览器会忽略 Content-Type 直接弹下载框，<img src> 只会拿到一个空壳 —— 图片根本显示不出来。
  • 预览不能计入 downloads，否则所有者看到的下载量虚高且无法排查。
  • 预览响应带 Cache-Control: no-store：内容受密码/提取码保护， 留在浏览器缓存里等于绕过校验就能再取一次。

为什么 fileId 必须校验整条祖先链

分享树只递归 2 层（listChildrenLimited(root.OwnerID, &root.ID, 2)）， 深层文件在 UI 树里看不见 —— 所以下载端点必须支持按 fileId 取任意深度， 但这正好给了越权构造的入口。

只查一层是不够的：孙目录、深层文件同样能被构造出来。 必须逐级向上，每层满足 owner_id == 分享所有者 && 未删除，最后落到分享根 ID。 maxDepth = 64 防 parent 成环导致无限回溯。

失败时不区分「不存在」与「越权」：告诉攻击者哪个 ID 存在本身就是信息泄露。

为什么 streamFile 要抽出来

登录下载（ownOrAdmin 校验）与分享下载（密码/提取码/祖先链校验）都要这套响应逻辑： 对象存储 302 签名跳转、Range 206、普通流式。 各自写一份的话，对象存储跳转与 Range 支持很容易只改一处 —— 而 Range 恰恰是视频拖进度条的前提。

测试

17. 改存储策略会把 SFTP 密码/云厂商密钥以明文写回库

做插件配置加密的占位调研时，顺手核对「Policy.Config 的加密路径是否可照抄」， 结果发现照抄不了 —— 因为它自己就漏了一条写入路径。

问题

controllers/admin_ex.go 的 UpdatePolicy 这样写：

db.Get().Model(&models.Policy{}).Where("id = ?", id).Updates(map[string]any{
    "name": req.Name, "type": req.Type, "config": req.Config, "is_default": req.IsDefault,
})

Policy.Config 是 models.Encrypted，加密靠 driver.Valuer（Value()）。 但 database/sql 只对实现了 Valuer 的「值」调用它 —— req.Config 是裸 string，Valuer 完全不参与，明文直接落库。

CreatePolicy/UpdatePolicy 之外的路径没问题：CreatePolicy 用了 models.From(req.Config)，User.TwoFactor 的两处写入 （controllers/auth.go:214,231）也都包了 models.From，旁边甚至有注释点了这个坑。 只有这一处漏了。

影响

policies.config 里存的是 SFTP 密码、OSS / COS / S3 密钥。管理员在后台 编辑一次存储策略，该策略的凭据就在数据库里变成明文 —— 而接口返回 200，GORM 不报任何错，日志也没有异常。

有兜底但不够：MigrateSensitiveFields() → migratePolicyConfig() 每次启动都会把 不带 enc:v1: 前缀的行转回密文。所以窗口是「编辑之后、下次重启之前」—— 不是永久泄露，但在两次重启之间密钥就是裸的，且期间任何一次库文件泄露都直接兑现。

为什么既有的测试没拦住

models/encrypted_test.go 的 TestEncryptedUpdateMapPath 注释写得很准 （「传裸 string，hook 完全拦不住，会静默写入明文」），但它传的是 models.From("NEWSECRET") —— 是个已带类型的值，所以它验证的是 「正确写法能加密」，而不是「错误写法会被拦」。测试名和注释比它实际覆盖的范围更大， 这种错位最危险：看名字以为这条路径已经有人守着了。

修复

"config": models.From(req.Config),

一行。另补两个测试锁住：

测试 作用
models/encrypted_bare_string_test.go 固化「裸 string 不被加密」这条 database/sql 约束，防止后来者把 models.From(...) 当冗余包装删掉
controllers/admin_policy_config_test.go 直接打 PUT /policies/:id，读原始列断言 enc:v1: 前缀

验证

两个测试都做过双向验证：把修复改回裸 string 后 TestUpdatePolicyConfigStaysEncrypted 报 policies.config 必须加密落库，实际 = "{\"password\":\"edited-by-admin\"}"（明文泄露）， 改回 models.From 后通过。测试必须在修复前失败才有价值。

对插件配置加密的直接影响

controllers/plugins.go 有两处同样的写法：

db.Get().Model(&p).Update("config", raw)          // 第 471 行，InstallPlugin
db.Get().Model(&p).Update("config", body.Config)  // 第 582 行，UpdatePluginConfig

今天 models.Plugin.Config 还是普通 string（字段本身就是明文），所以现在不是 bug。 但一旦按计划把它改成 models.Encrypted，这两处必须同时包成 models.Encrypted(...)，否则插件配置（SMTP 密码、HMAC sharedSecret） 会重演本节这个 bug。已写进 docs/新功能占位清单-明天接续.md §2.5。

18. 插件冒烟测试从来没跑到过插件部分

上一节修完需要端到端验证（包级测试读不到"真实 HTTP 接口 + 真实 SQLite 原始列"）， 于是先跑现有的 backend/smoke_plugin.sh，结果它在第 2 步就死了：

也就是说：仓库里唯一的插件端到端测试从未真正验证过任何插件行为， 但它在文档里被当作已有覆盖。

18.1 smoke_plugin.sh 的四类缺陷

# 缺陷 后果
1 BIN="./.smoke-nebula" + go build -o "../$BIN" → 产物建到仓库根，运行时又去数据目录上一级找 第 2 步即挂
2 产物不带 .exe Windows/Git Bash 起不来
3 -data . + 库路径 data/nebula.db → conf 只 MkdirAll(".")，./data 不存在 sqlite 报误导性的 out of memory (14)
4 安装插件时把 MSYS 路径 /e/... 塞进 JSON 服务端按原生路径解析找不到目录 → 400
5 钩子计数匹配 "name":"onAntiLeech","inProcess":0,... 连续子串 gin.H 是 map，encoding/json 按字母序输出键（…mode/name/outProcess…），该子串永远不可能命中
6 kill -0 "$PLUGPID" 判断插件子进程 Windows 下插件 pid 是原生 PID，bash 的 kill -0 只认 MSYS pid → 明明在跑却报"不存在"
7 无 .exe 意识、只 kill 子 shell 残留真实进程占着端口与数据目录（Device or resource busy）

修法：路径全部基于 $(dirname "$0") 解析；按 uname -s 补 .exe； 不传 -data（用默认数据目录，与真实安装一致）；加 jsonpath()（cygpath -w + 反斜杠转义）；钩子断言改成先拆分对象再匹配；加 proc_alive() 平台分流； 清理时 taskkill //F //IM 兜底。

修好后 20/20 通过，插件热加载链路（安装 → 启用拉起子进程 → 403 拦截 → 禁用回收子进程） 第一次被真实验证。

18.2 顺带发现：装完不重启，插件功能全部 503

修好脚本后卡在「启用 → 503」。查明原因：

main.go 的 bootstrap()（db.Init、版本化迁移、pluginset.InitPlugins、jwt.Init） 只在启动时 conf.IsInstalled() 为 true 才执行。而首次安装是在服务运行中 通过 POST /api/install 完成的 —— 此时 bootstrap 早已跳过。

所以"装完向导不重启"= 插件宿主始终为 nil，所有插件接口 503（前端显示"插件宿主未就绪"）。

脚本里的处理是按真实部署方式重启一次（新增 [3b/7] 步骤），并断言重启后 /api/admin/plugins/hooks 能返回 protocolVersion。

这属于产品既有行为，不是脚本缺陷，因此本轮只记录不改：是否要让安装流程 自己补一次宿主初始化（或提示管理员重启），需要产品决策。

18.3 新增 smoke_policy_config.sh

第 17 节那个明文泄露 bug 的端到端守卫。它从真实 HTTP 接口打进去， 再直接读数据库原始列断言 enc:v1: 前缀：

检查 说明
Create 后原始列为密文 覆盖 models.From 正确路径
Update 后原始列仍为密文 覆盖出过事的那条路径
数据库文件（含 wal/shm）无明文密钥 第二道防线，逐个文件判断而非 glob（glob 不匹配会把"没匹配上"误判成"没泄露"）

最后一项不能靠"读接口拿配置"：models.Policy.Config 的 tag 是 json:"-"， 接口刻意不返回配置（不把密钥发给客户端是对的）。改用 filesystem.New(p.Type, p.Config.String()) 需要明文 JSON 这一点来间接验证 —— 若 Config.String() 返回密文，JSON 解析失败 → 上传 500。

18.4 教训

"脚本存在"不等于"脚本在跑"。 这两处覆盖（插件端到端、密钥静态加密） 在修复前都属于"看上去有、实际零"的状态。冒烟脚本本身也会腐坏， 而它腐坏时不会发出任何信号 —— CI 不跑它们，没人执行它们， 于是坏了好几个月也没人知道。

18.5 把冒烟接进 CI（新增 .github/workflows/smoke.yml）

光修好不够 —— 没人定期执行，它们迟早再次腐坏。新增独立 workflow：

步骤 内容
Plugin hot-reload smoke bash backend/smoke_plugin.sh
Policy config encryption smoke SMOKE_REQUIRE_SQLITE3=1 bash backend/smoke_policy_config.sh

几个刻意的选择：

  • 单独一个 workflow，不塞进 go-ci.yml：go-ci 是 vet + test -race（秒到分钟级）， 冒烟要起真实进程、建真实 SQLite、走真实 HTTP。混在一起会让 "单元测试挂了"和"端到端挂了"难以区分。
  • 触发路径含 examples/plugins/**：示例插件是独立 module，go-ci 覆盖不到它， 而冒烟会现场编译并加载它 —— 这里顺带补上了那块空白。
  • SMOKE_REQUIRE_SQLITE3=1：smoke_policy_config.sh 的核心断言依赖 sqlite3， 本地缺依赖时默认跳过（不阻塞开发机）；但 CI 里必须失败。 否则门禁会变成"永远绿色"的假门禁 —— 正是本节的病根。已本地验证两个分支： 严格模式退出码 1、宽松模式退出码 0。
  • EXIT trap 里的 rm 补 || true：set -e 下 trap 中任何一条非零命令都会 覆盖脚本真实退出码，把"断言失败"伪装成"清理失败"。

20. 公开分享的防盗链缺口已补（onAntiLeech 覆盖分享下载与预览）

第 17 节的调研顺带发现的缺口，本轮实现。

问题

onAntiLeech 原先全项目只有一个调用点（controllers/file.go 的 Download）， 而公开分享走 controllers/share.go 的 serveShareFile —— 完全不触发该钩子。

后果：装了防盗链插件的站点，分享链接依然可以被任意第三方站点盗刷。 而分享恰恰是最需要防盗链的场景：站内下载要登录，分享链接是公开的。

修法

在 serveShareFile 里、target 解析并通过祖先链校验之后、 handlerForFile(&target) 之前新增调用点。位置理由是硬的：

  • 更早：target 与分享还没解析出来，拿不到 fileId / fileName / shareId；
  • 更晚：文件已进入 streamFile 开始流式输出，再想 403 已经来不及。

为什么 preview 也必须过闸（本轮最关键的一个决定）

preview 用的是 Content-Disposition: inline，看起来"只是预览"， 但它返回的是完整文件内容。只拦 download 等于留了一条完整的 绕过防盗链的通道 —— 攻击者拿 ?fileId= 打 preview 就能把文件拖走。

这个判断不靠推理，靠实测：把闸门改成"只拦 download、放行 preview"后， 测试直接报出了证据 ——

--- FAIL: TestShareAntiLeechBlocksDownloadAndPreview
    share_antileech_test.go:126: 分享**预览**未被防盗链拦截: status=200 body=hello share

于是宿主对两者一视同仁地过闸，并把场景通过 shareKind （download / preview）交给插件自己决定要不要区别对待。 宿主不替插件做这个取舍，但绝不默认放行其中一个出口。

ctx 契约（分享路径）

{userId: 0, userName: "", ip, ua, fileId, fileName, referer,
 shareId, shareKind, shareOwnerId}

两个刻意的点：

  • userId 恒为 0 且键必须存在。分享访问者是匿名的，插件不能假设它有值。 键存在与键缺失是两种语义：键缺失时插件的 numOf(ctx["userId"]) 拿到 nil， 与"存在且为 0"不同。测试专门断言了"键存在且为 0"。
  • 分享所有者放 shareOwnerId，不与访问者混淆 —— 登录下载那条路径里 userId 就是所有者，两个路径的语义不同，共用同一个字段名会造成误判。

拦截判定走 plugin.IsBlockedError（hooks.go 声明它是全项目唯一实现）。

22. 接通 onApiAuth：开放 API 的扩展鉴权

第 3 个预留钩子（Wired=false）接通。用途：/api/v1/* 在内置鉴权 （PAT / OAuth2）之外接受扩展鉴权方案 —— HMAC 签名、IP 白名单、 第三方令牌等。

设计计划被推翻：不需要同步门

第一版计划写的是"照 onRateLimit 的做法加一个同步门（APIAuthGate）"。 实现时发现前提不成立：

onRateLimit 之所以要另开门，是因为它有 7 个调用点、只有 1 个需要读结果 —— 把整个钩子改成同步会让另外 6 处每次白等一次 IPC 往返。 而 onApiAuth 只有一个调用点，且它必须读结果。

所以正确做法就是把它本身改成 ModeSync + Blockable: true， 不需要任何额外的门。计划里"照抄某个模式"的指令，先要核对前提是否相同。

接线位置与语义

落在 middleware/api_auth.go：PAT / OAuth2 都失败之后才触发。两个原因：

  • 热路径零成本 —— /api/v1/* 的每个请求都走这个中间件， 正常鉴权不该为一次 IPC 往返买单；
  • 内置凭据始终优先，插件无法否决一个已经有效的令牌。

插件有两种表达方式：

意图 做法 宿主行为
放行 在 ctx 写入 principalUserId（>0） 从库里取出该用户设为当前用户
拒绝 返回含 blocked 的 error 403
不表态 两者都没有 保持 401（fail closed）

拒绝用 403、未表态用 401：前者是"扩展鉴权明确说不"，后者是"凭据没通过"。

ctx 契约

{method, path, query, ip, ua, headers, hasAuthorization,
 contentType, contentLength, bodyHash, bodyTruncated}

两个刻意的决定：

  • headers 不含 Authorization。 内置凭据留在宿主这边；插件要用自定义凭据 应当用自己的头（HMAC 签名正是这样）。这既减少凭据扩散面，也逼出一个明确约定， 而不是让插件去猜"Authorization 里的东西算不算已经验证过"。
  • bodyHash 有上限（64KB）。 本中间件在鉴权失败时才跑到扩展鉴权， 而失败路径是攻击者可控的：不限量读 body 等于给了一个内存放大面。 超限时不读全文，只置 bodyTruncated=true 并把 bodyHash 置空 —— 半截数据的哈希没有任何意义，给出去只会让插件拿错误的哈希去校验 （然后表现为"签名永远不对"）。

bodyHash 还有一个必须做对的细节：中间件"顺手看一眼" body 之后， 后续 handler（例如 /api/v1/files/upload）仍要读到完整内容。 用 io.MultiReader(已读缓冲, 原body) 放回，读完与截断两条路径都不丢字节。 测试里专门发了一个带 body 的请求并断言下游读到的内容一字不差。

一个只会在"多进程"下暴露的静默失效

principalUserId 的值必须兼容多种数字类型：进程内 handler 写进去的是 Go 的 int/uint，而进程外插件的回写经 JSON 往返后是 float64。 只认其中一种的后果是"进程外插件放行无效"，而且不报任何错 —— 这类静默失效正是本项目插件体系里反复出现的一类坑（参见 referer-guard 里对 ctx["userId"] 的同类处理）。

float64 路径额外加了 2^53 与整数性校验：JSON 无法精确表示更大的整数， 拿到的值可能已被四舍五入成另一个用户。int 路径没有这个歧义 （它来自进程内、是精确值），所以那里的界限只要求为正 —— 这个不对称 是有意的，测试里也写了注释说明。

23. hmac-auth 从契约探针变成真的会鉴权

第 22 节接通 onApiAuth 后，本轮把插件的校验实现补上。 至此 /api/v1/* 除了 PAT / OAuth2，还能用共享密钥 + HMAC-SHA256 签名调用。

端到端测试抓出一个只能靠真实请求发现的 bug

实现完成、包级测试全绿之后，冒烟脚本里的签名请求一直返回 401。 现象极具迷惑性：

  • 插件进程在跑（status: running、真实 pid）；
  • 钩子计数正确（outProcess: 1、mode: sync）；
  • 插件日志里一片空白 —— 连一条"收到 onApiAuth"都没有。

也就是说：钩子注册了，却从未被派发。

根因在接线位置：APIAuth 原本在

tok := extractBearerToken(c)
if tok == "" {
    c.AbortWithStatusJSON(401, "missing token")
    return          // ← 扩展鉴权在这后面，永远到不了
}

而 HMAC 客户端压根不会带 Authorization 头（签名放在自定义头里）。 于是所有这类请求都在第一步就被 401 挡掉，扩展鉴权形同不存在 —— 而且返回的 401 看起来完全正常，没有任何异常信号。

修法：把"缺 token 就早退"改成延迟到最后兜底，让扩展鉴权在 内置方式全部失败（含根本没带凭据）之后都能拿到请求：

if tok != "" { /* 1. OAuth2 */ }
if tok != "" { /* 2. PAT    */ }
switch u, decision := pluginAPIAuth(c); decision { /* 3. 扩展鉴权 */ }
if tok == "" { 401 "missing token" } else { 401 "invalid token" }

已补回归测试 TestAPIAuthPluginWithoutAuthorizationHeader —— 断言"不带 Authorization 的请求必须能走到扩展鉴权"，并在注释里写明了 这个坑的症状，避免以后有人"优化"时又把早退加回去。

教训：包级测试覆盖了所有逻辑分支，却覆盖不了接线位置。 这次能发现，靠的是端到端脚本里那条真实 HTTP 请求。

签名规范串

METHOD\nPATH\nQUERY\nTIMESTAMP\nBODY_SHA256_HEX

五行，缺一不可。少任何一行，攻击者就能在不改签名的前提下替换那部分内容。 测试里用"篡改表"逐项验证：改方法 / 路径 / 查询串 / 请求体摘要 / 时间戳 / 签名 / 换密钥，每一项都必须被拒。

反向验证：把 bodyHashHex 从规范串里去掉后，篡改表里"改请求体摘要" 当场报红（该字段没有被纳入规范串）—— 证明这张表不是摆设。

  • manifest.json（库信息 + 文件清单，上限 2 万条并标记 truncated）。

onRestore —— 暂存制

POST /api/admin/backup/restore（挂 RequireConfirm，与卸载插件同门槛）。

关键设计：恢复不当场替换数据库。热替换正在被使用的 SQLite 库 （活动连接 + WAL）会直接损坏数据，这不是保守，是唯一安全的做法。 所以接口只做三件事：

  1. 解 zip、找 nebula.db 条目；
  2. 校验 SQLite 文件头 —— 不校验就写进数据目录，等于允许把任意内容 伪装成数据库，下次启动直接打不开；
  3. 写进 data/restore/ 并留下 PENDING 标记。

真正的替换发生在下次启动，由 ApplyPendingRestore() 在 db.Init 之前执行（那时本进程还没打开库，换文件是安全的）。原库会被改名保留 （.pre-restore-<ts>），出问题能手工回滚；-wal/-shm 一起挪走 —— 只挪主文件会留下不一致的 WAL。挪不动现库时直接放弃，不硬覆盖。

onRestore 在提交时触发。同样写明"插件在此拦不住这次恢复"， 需要否决请在权限层解决 —— 而不是让人对着一个异步钩子写拦截逻辑然后困惑为什么没用。

onCLI —— 第一个真正的子命令

引入 nebula plugin <cmd> [args...]。放在 flag.Parse 之后， 这样 -data 这类全局参数在子命令里照常可用；放在之前会让子命令 自己解析参数，两套解析迟早打架。

onCLI 是 ModeSync + Blockable（与另两个不同）：命令行必须拿到输出。 插件往 ctx 写 cliOutput（打印）与 cliExitCode。退出码约定 0 成功 / 1 用法错误或被插件拒绝 / 2 未安装，让脚本能安全地 nebula plugin x && ...。

子命令不启动 HTTP 服务：初始化依赖 → 派发 → 退出（冒烟里有断言）。

26. PBClus：插件包的独立容器格式 + 打包工具

需求是"最终可识别的插件格式是 .PBClus，不是 zip 改个后缀"。

先说明一件事实：PBClus 在本仓库此前零命中 —— 它不是项目已有的格式， 所以这一节做的不是"接入"，而是定义一个新格式并实现它。

为什么"改后缀"不算数

改后缀只换名字，格式仍然是 zip：解析规则、攻击面、允许的结构全都没变。 而且更糟 —— 文件名叫 .pbclus 内容是 zip，会让"看到 .pbclus 就知道怎么处理" 这件事变得不可靠。所以这里定义的是真正不同的容器：

维度 zip PBClus v1
路径规则 解压方各自防 格式层规定：相对、规范化、纯正斜杠，../绝对路径/a//b 打包即拒
条目类型 文件/目录/符号链接/设备 只有普通文件与目录（消灭 symlink 一类攻击）
重复路径 允许，结果取决于实现顺序 拒绝
条目排列 任意，可有空洞 必须紧密连续，有空洞/重叠即判损坏
校验 每条目 CRC32 头部 CRC + 清单/载荷 SHA-256 + 尾部整文件 SHA-256 + 逐条目 SHA-256
识别方式 扩展名 魔术字（PBClus + 0x1A 0x0A）

布局：[Header 128][Manifest JSON][Payload][Footer 48]，小端。 魔术字末尾用 0x1A（DOS EOF）与 0x0A 是学 PNG 的老办法： 文件被文本模式工具糟蹋过时立刻暴露，而不是解出一堆乱码。

校验的边界（写进文档，避免制造错觉）

CRC 与 SHA-256 只保证完整性（没损坏/没截断），不提供防伪 —— 任何人都能重新打包并算出正确摘要。v1 没有签名，flags 保留位留给将来扩展。 装插件时它仍是不可信输入。这一点在 HTML 文档里用单独一张 danger 卡写明。

打包工具

新增 backend/cmd/pbclus-pack（go build -o ../tools/pbclus-pack.exe ./cmd/pbclus-pack）：

pack <目录> [-o 输出] [--store] [--level N] [--include-all] [--force] [--quiet]
inspect <包> [--json]     verify <包>     unpack <包> -o <目录>     info

退出码 0 成功 / 1 失败 / 2 用法错误 —— 让打包能写进脚本。

pack 会先用与宿主同一套校验检查 plugin.json，清单问题在打包阶段暴露， 而不是等管理员点安装。默认排除版本库/依赖目录/编辑器临时文件/其它压缩包。

安装侧

InstallFromPackage 按魔术字识别（不看扩展名），路由到 PBClus 或 zip； 两条路在"解包到临时目录"之后汇聚到同一个 InstallFromDir， 所以清单校验、插件名检查、落库语义只有一套。 管理端 source: local 现在同时接受目录与包文件。

zip 改名成 .pbclus 会被明确拒绝，并直说"改后缀不会改变格式， 请用 pbclus-pack 重新打包" —— 用户改后缀的意图很明确，错误信息要正面回应它。

实现过程中发现的三个问题

① ExecPath(".") 误报"entry 越界"（既有 bug）。 ExecPath 用 filepath.Clean 算前缀，dir="." 时 base 是 "." 而 p 是 "entry"， 前缀判断失败。生产路径下 PluginsDir/name 是多段路径所以看不出来， 但 pbclus-pack pack . 这种人最自然的写法直接撞上。已改为两侧都 filepath.Abs （与 install.mustBeUnder 的判定方式一致），并补回归测试 TestExecPathWithDotDir。

② 打包工具自己又实现了一遍入口检查。 写 pack 时顺手写了 os.Stat(dir/entry)，漏了 Windows 的 .exe 补全， 于是"referer-guard.exe 存在、清单写 referer-guard"被误报成"入口不存在"。 改成调用宿主自己的 man.ExecPath() —— 跨平台后缀解析只有一处实现，就必须只有一处。 这是同一种错误第二次出现（§17 的裸 string、§25 的重复 onCLI）， 共同点都是"另写一遍已有逻辑"。

③ flag 包不接受"位置参数后面跟选项"。 pack . -o out.pbclus 报用法错误，而我的用法提示写的正是这种顺序。 Go 的 flag 在遇到第一个非 flag 参数后停止解析。没有要求用户改习惯， 而是加了 reorderArgs（按每个子命令的布尔选项表，把 flag 搬到位置参数之前）。

27. PBClus v2：跨平台包 + 签名

第 26 节的两条遗留（"一个包只能给一个平台"、"没有签名"）本轮一起解决。 两件事都是格式变更，合并成一次版本升级（v1 → v2），而不是加两个可选字段。

为什么必须升版本，而不是"加个可选字段就行"

v1 的解析方不认识平台字段。如果只加字段不升版本，老宿主会把所有平台的 二进制都解到同一个路径上，最后写进去的那个胜出 —— 于是 静默装上一个架构不对的二进制，表现为"插件启用后立刻崩"或 "入口不存在"，完全没有线索指向真实原因。

升版本让老解析方直接拒绝（版本 %d 不受支持），而不是做错事。 这正是版本字段存在的意义：兼容性判断要在"能不能安全地读"这一层做， 而不是指望每个解析方都恰好忽略新字段。

读取侧支持 1~2（MinReadVersion=1）：v1 包的条目天然都是通用文件， v2 的读法能完整覆盖它的语义，所以不需要维护两套解析逻辑。

跨平台

条目新增可选的 platform 字段（<goos>/<goarch>，空 = 通用）， 清单新增 platforms 声明。同一路径可以有多份不同平台的条目 —— 唯一性判定从"路径"改成"(路径, 平台)"，这是多平台包的核心机制。

安装器在解包之前就检查 Supports(当前平台)，不支持时给出：

这个插件包不支持当前平台：包内含 linux/amd64、windows/amd64，当前是 darwin/arm64。
用 pbclus-pack pack --targets darwin/arm64,... 重新打包即可做成跨平台包

顺序是刻意的：先解包再报"入口文件不存在"会把排查方向完全带偏 —— 那个错误看起来像"打包漏了文件"，真实原因是平台不匹配。

打包工具侧的原则是不猜：

情况 处理
入口不是原生可执行文件（脚本/字节码） 通用包
入口是原生可执行文件，且与当前主机同类型 标注当前平台
入口是原生可执行文件，但类型与主机不一致 报错，要求显式 --platform

最后一条是关键：在 Linux 上打一个 Windows 的 .exe，自动标成 linux/amd64 会让包带着错误信息流通出去。报错只让你多打一行参数，猜错的代价是装上一个 跑不起来的二进制 —— 这个交换明显划算。

--targets a,b,c --build 会交叉编译到临时目录再打包（不污染作者的源码目录）， 一次产出一个真正跨平台的包。实测 referer-guard 三平台包： 9.9MB → 5.7MB（58%）。

平台后缀解析只有一处实现（宿主的 ExecPath）。打包工具自己又写了一遍 os.Stat(dir/entry)，漏了 Windows 的 .exe 补全，于是 "referer-guard.exe 存在、清单写 referer-guard"被误报成"入口不存在"。 这是同一种错误第三次出现（§17 裸 string 绕过加密、§25 重复的 onCLI）， 共同点都是"另写一遍已有逻辑"。

签名

定长 108 字节的签名块，位于载荷之后、尾部之前，有无由头部 flags 决定：

偏移  长度  字段
   0     1  算法（1 = Ed25519）
   1     3  保留
   4     8  keyId（公钥 SHA-256 前 8 字节）
  12    64  签名
  76    32  公钥

定长是刻意的：Ed25519 的签名恒 64 字节、公钥恒 32 字节，所以"有没有签名" 一个 flags 位就够，不必为签名去改头部布局。

签名消息 = "PBClus/v2 signed-package\n" ‖ fileSHA。 签名块自己不在被签内容里（否则自指），所以"先算摘要再签名"没有循环依赖。 尾部 fileSHA 的覆盖右边界也随之明确为 contentEnd（不含签名块）。

这一段是全文最重要的设计说明：签名 ≠ 可信

公钥内嵌在包里。因此任何人都能签一个"验证通过"的包 —— 用自己的密钥签，把公钥一起放进去，Valid 就是 true。

所以状态被拆成三个独立字段，不给"顺手用错"留空间：

状态 含义 能否用于安全决策
完整性 没损坏、没截断 ❌ 攻击者能同步所有公开摘要
Valid 内容与签名自洽 ❌ 任何人都能签出 Valid 的包
Trusted keyId 在宿主信任库里 ✅ 唯一能用于决策的

安装器只用 Trusted 判定。宿主没有信任库时不会信任任何签名 （不会退化成"信任所有签名"）。

最有力的证据在测试里：TestSignatureCatchesWhatIntegrityCannot 构造了 "攻击者改完内容后把所有公开可算的校验数据全部同步一遍"的包 —— 条目摘要、清单摘要、载荷摘要、头部 CRC、尾部整文件摘要全部重算 —— 此时 Verify() 通过，而只有签名会失败。如果签名只是 "和摘要比一比"，这条用例就会漏掉。

签名策略 off/warn(默认)/require，配置项 plugin.signatureMode。 默认 warn 的理由：require 会让所有存量无签名插件在升级后立刻装不上， 而建立信任库需要管理员先操作一步。策略值写错时按 require 处理（fail closed）—— 配置笔误不该悄悄降低安全门槛。

工具侧补齐信任管理的两端

签名只是密码学，信任才是安全语义所在。所以工具提供了两端：

pbclus-pack keygen -o key.json --name 发布者      # 发布者生成密钥
pbclus-pack pack ./myplugin --sign key.json       # 签名打包
pbclus-pack trust add --key key.json --name 发布者 # 管理员建立信任
pbclus-pack verify pkg.pbclus --trusted-keys trust.json

verify 在没有信任库时明确说"Ed25519 有效 —— 未提供信任库， 无法判断是否可信"，而不是含糊的"通过"。把"签名有效"讲成"可信" 是这类工具最危险的表述。

信任库文件填了 publicKey 就必须与 keyId 自洽 —— 否则会出现 "keyId 写的是可信发布者、公钥却是别人的"，等于信任了一个冒充者。

28. 信任管理入口 + 一个"插件重启后消失"的既有 bug

上一节留的两条遗留（"第一次怎么建立信任"、"没有撤销机制"）其实是同一个 缺口：签名在格式层做完了，但没有人能操作信任。同时补掉的还有一个 在写这组测试时撞出来的既有 bug（比新功能本身更重要）。

28.1 顺手发现并修掉的既有 bug：安装侧与加载侧用了两个不同的数据目录

写信任库路径的测试时发现 trustStorePath() 与 conf.DataDir() 对不上， 顺着查下去发现根因不在信任库，而在整个插件子系统：

用的路径
加载侧 pluginset.InitPlugins conf.DataDir()/plugins
安装侧 controllers.pluginsRootDir() dataDirOrCwd()/plugins

而 dataDirOrCwd() 只认环境变量 NEBULA_DATA_DIR，取不到就退回进程工作 目录 —— 而 NEBULA_DATA_DIR 在整个仓库里从未被设置过（我全仓 grep 过）， 所以它实际上永远返回 cwd，把 -data 指定的数据目录完全忽略掉。

后果不是"插件装不上"，而是更隐蔽的一种：

  • 安装 + 启用当场完全正常（控制器两处都用自己那套路径，自洽）；
  • 重启服务后启动加载在另一个目录里找不到插件，且没有任何错误提示；
  • 管理员看到的是"插件昨天还好好的，今天启动就没了"。

冒烟测试抓不到它：脚本只在安装向导之后重启一次（那时还没有任何插件）， 装完插件后又从不重启。所以这个 bug 能一直活着。

修法是把 conf.DataDir() 作为唯一事实来源；NEBULA_DATA_DIR 保留为 显式覆盖（容器部署里指向挂载卷是常见做法，那种场景下 cwd 与数据目录 本来就不同）。conf.DataDir() 是备份、密钥、数据库文件用的那个路径， 插件没有理由另搞一套。

两条独立验证： 1. 单元测试断言"安装侧算出的插件目录 == 加载侧算出的目录" （TestPluginPathsAgreeWithLoader）——修复前 FAIL，报 加载侧: <temp>/plugins / 安装侧: E:\nebula-drive\backend\controllers\plugins； 2. 冒烟新增第 9.4 节：启用一个插件 → 重启服务 → 断言它自动恢复运行 （70/70）。这条同时覆盖了"PBClus 安装 → 启用 → 重启后恢复"整条链路。

顺带说一句：我第一版 9.4 的断言前提是错的 —— §7 结束时插件已被禁用、 §9 收尾也禁用了包安装的那个，所以重启前根本没有启用的插件， 断言测的是空气。冒烟当场报了 2 个 FAIL，我改成"先启用 → 再重启"才是有效断言。 这类"前提不成立"的测试比没有测试更危险，因为它会给出虚假的安心。

28.2 信任管理：从"手工放文件"变成可操作的动作

之前建立信任的唯一办法是把 plugin-trust.json 手工放进数据目录。能用， 但两个实际问题：管理员看不到现状；改策略要手改配置文件， 而写错一个值（Require 大写）会按 fail closed 处理，表现为"插件突然都装不上"， 原因很难找。

新增四个管理端接口（全部落审计）：

方法 路径 作用
GET /api/admin/plugins/trust 策略 + 信任库内容 + 已安装插件的签名统计
POST /api/admin/plugins/trust 加公钥（或 keyId）
DELETE /api/admin/plugins/trust/:keyId 移除（= 撤销）
PUT /api/admin/plugins/trust/mode 改策略

几条刻意的设计：

  • 接口只接受公钥，不接受私钥。发布者的密钥文件里同时含私钥与公钥， 而"把你的密钥文件发给我"是极自然的说法 —— 一旦照做就是私钥泄漏。 所以接口挡掉 64 字节的私钥输入，并明确说"这看起来是私钥，请用 *.pub.json 里的 publicKey 字段"。同时 keygen 额外写一个只含公钥的 分发文件（<名字>.pub.json，0644 权限），让"该发哪个文件"没有歧义。
  • 信任库坏了不许静默重建（409 而不是覆盖）。静默重建会把管理员已有的 信任关系一次抹掉；而且列表接口要如实把错误报出来，不能显示成"空库" —— 后者会让管理员以为自己配的信任丢了。
  • 切到 require 要二次确认（409 + needConfirm），因为存量无签名插件 会让后续所有安装被拒。这里有个自己踩的坑：第一版在提示里写了 "带 confirm=true"却没读这个字段，导致该分支下 require 永远设不上 —— 提示与实现必须一致，测试把它抓出来了。
  • 只登记 keyId 是允许的，但要给出诚实提示：keyId 是公钥的摘要， 无法反向校验，挡不住"同一个 keyId 配了别人的公钥"。

28.3 签名状态必须落库（包文件安装后不保留）

插件包安装完就只剩解出来的文件，签名状态事后无法从磁盘重新推导。 所以新增两列（Plugin.Signature JSON 快照 + Plugin.Trusted 布尔）在安装 那一刻记下来，列表接口把它解析成 signatureInfo 供界面展示。

为什么不每次从 JSON 里现解析布尔值：当时是否受信任这个判定结果要被 冻结下来 —— 事后往信任库里加一个 keyId，不应改变历史记录。 这也是"审计"与"现状"的区别。

28.4 一处顺带的安全提示修正

SetPluginSignatureMode 采用"整份复制再改、只有 Save 成功才换内存配置"的 写法。如果就地修改 Current() 返回的对象再 Save，会出现 "写盘失败但内存里已经变了"的半状态 —— 表现为"界面显示已改、实际没生效、 重启后又变回去"。conf.Save 会把传入指针直接挂成 current，所以必须传副本。

28.5 顺带修掉的第二个既有 bug：前端 request() 丢掉了错误响应体

给信任界面接 409 的二次确认时，前端同学发现 client.ts 的 request() 是这样的：

if (!res.ok) {
    const msg = (data && data.message) || res.statusText
    throw new Error(...)          // ← 只有 message，结构化字段全丢了
}

而 Plugins.tsx 里有 5 处在读 e?.data?.needAgreement：

Plugins.tsx:121/146/166/187/211   if (e?.data?.needAgreement) return handleNeedAgreement()

data 从来没被挂到错误对象上，所以这 5 处全是死代码。后果是真实的： 后端在插件协议未接受时返回 403 + needAgreement（plugins.go:213/535）， 而前端把响应体一丢，只能显示一条普通错误 —— 协议弹窗永远不会弹出来。 管理员看到的是"启用失败"，而不是"请先阅读并同意协议"。

29. 四个能用的插件（覆盖 6 个此前没有示例的钩子）

之前仓库里的示例插件只有三个（referer-guard / smtp-email / hmac-auth）， 覆盖 onAntiLeech、onEmail、onApiAuth。其余钩子一个可运行示例都没有 —— 对插件作者来说等于"这些钩子怎么用，自己看源码猜"。

本轮补了四个，都是能直接用的（不是骨架），并各自覆盖一个新钩子：

插件 钩子 干什么
notify-webhook onEmail + onCLI 把站内通知转发到 Slack / 飞书 / 钉钉 / Discord / 通用 webhook
backup-mirror onBackup + onRestore + onCLI 备份包的异地镜像 + 轮转 + 恢复审计
download-limiter onAntiLeech + onCLI 按 IP 的滑动窗口下载限流，防批量抓取
collab-redirect onCollabOpen + onCLI 把协作编辑 302 跳转到 OnlyOffice / Collabora

四个都实现了 onCLI，所以都能用 nebula plugin <name> 做自检 —— 这既是运维手段，也顺便把 onCLI 从"只有测试夹具用过"变成"有真实示例"。

统一的设计约束

  • 只用标准库，go.mod 里没有 require。插件是独立 module， 引入依赖就等于让用户为了一行功能去下载一堆包。
  • stdout 只放 RPC，日志一律 stderr（混用会破坏分帧，插件直接失联）。
  • ctx 里的数字一律按 float64 读（JSON 往返后的形态），断言成 int 会静默失败。
  • 失败要么诚实失败（notify-webhook 未配置时退出码 1 并说明怎么配）， 要么 fail-open 但记日志（backup-mirror 复制失败不阻塞宿主）—— 不允许"静默成功"。

几个值得单独记下来的实现取舍

backup-mirror - 轮转只删匹配 ^backup-\d+-[0-9a-f]{8}\.zip$ 的文件。target 目录是用户 自己选的，很可能还放着别的东西 —— 一个"清理旧备份"的工具顺手删掉用户的 文件是不可接受的。轮转时还用 ReadDir + Type()&os.ModeSymlink 跳过符号链接， 防止有人在 target 里放个指向 /etc 的链接让插件去删系统文件。 - 写入走 .part → fsync → 重算摘要 → rename，校验不过就删文件且不计入轮转。 - keep 缺省是 0（不轮转）而不是 7：Go 零值无法区分"没写"与"显式 0"， 而默认删旧备份的风险明显高于默认不删。

download-limiter - 用滑动窗口而不是计数器清零。固定窗口在边界上会放过 2 倍流量 （窗口末尾打满 + 下个窗口开头打满），这是限流实现最常见的错。 - 有 maxTrackedIPs 上限并淘汰最久未活动的 IP。这不是优化而是安全要求： 没有上限时，攻击者用海量伪造 IP 就能把限流器的内存打爆 —— 限流器自己成了 DoS 面。 - 只在拦截时记日志。下载是高频操作，每次都记会淹掉管理端的 500 条日志缓冲。

collab-redirect - 占位符替换的值必须 URL 转义：文件名里有 &、空格、中文、# 都是常态， 不转义会破坏查询串甚至造成参数注入。测试里用 报告 & 附表.docx 验证。 - 不匹配就必须什么都不写。宿主只要看到 ctx["url"] 非空就 302， 乱写会把本站自己的 md/txt 协作也劫持掉。 - 渲染结果必须校验是 http/https 且有 host，否则不跳转 —— 配置写错时 302 到 javascript: 之类的地址是真实风险。

notify-webhook - 拒绝 HTTP 重定向（3xx 视为失败）：webhook 入口通常不带重定向， 跟着跳转只会把载荷发到意料之外的地方。 - 日志里 URL 脱敏成 scheme://host/…。webhook URL 往往自带凭据 （Slack 的 token 就在路径里），而插件日志会展示在管理端。

遗留（如实记录）
