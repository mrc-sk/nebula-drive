3. 关键设计决策（明天别推翻）

3.1 为什么用子进程而不是 Go plugin.Open

plugin.Open 只支持 Linux/macOS 且需 cgo —— Windows 根本编译不了， 而本项目日常在 Windows 开发、要打包给 Linux 朋友。WASM 需 CGO， Go host function 绑定成本过高。子进程方案跨平台、崩溃隔离、真热插拔。

3.2 12 个 plugin.Fire 调用点一行都没改

靠 Hooks 表里的 Mode 字段分流： - ModeSync（onAntiLeech / onCollabOpen）：阻塞等 IPC 结果 - ModeAsync（其余）：每插件一个 goroutine，结果不回传 （业务已经继续往下走了，回写 ctx 只会造成竞态）

onRateLimit 是矛盾点（7 处调用但只有 1 处检查返回值）， 当前取 ModeAsync + Blockable:false —— 即中间件那处的插件拦截暂不生效。 这是个已知的待办，见 §5.3。

3.3 Fire 不持锁执行用户代码

旧实现 Fire 全程持 mu.RLock()，若在锁内做 IPC 往返（可达数百 ms）， Register 和 List 会被卡死。新实现先 snapshot() 复制 handler 再放锁。

3.4 拦截语义保持字符串匹配

strings.Contains(err.Error(), "blocked")（大小写敏感）。 FireResult 故意没有 Blocked 字段，让进程内/进程外两种形态语义完全一致。

5.1 示例插件端到端测试被跳过

example_test.go 用 t.Skip 保护。原因是它需要 go build 现场编译， 我给了它独立的 go.mod 后还没重跑验证。明天第一件事：

预期 TestRefererGuard_EndToEnd 的 4 个子用例全过。

5.2 Config 字段是明文

plugins.config 存明文 JSON。协议第五节已向管理员明示， 但更好的做法是用项目现成的 AES 加密（conf 里已有，参考 MigrateSensitiveFields）。 优先级低，但值得记。

5.3 onRateLimit 的插件拦截未生效

如 §3.2 所述。解法：在 middleware/rate_limit.go 改用 plugin.RateLimitGate(ctx) —— 一个同步接口，内部对 async 钩子做有超时的等待。 没写，明天做。

5.4 IsLoopbackAddr 未被使用

install.go 里有这个函数，IsInternalAddr 才是实际用的那个。 明天清理死代码（或删掉，或在商店接口里用来给管理员提示内网风险）。

5.5 崩溃重启的退避最长 5 分钟

restartMaxDelay = 5 * time.Minute。连续崩溃 5 次后停止自动重启。 如果觉得 5 分钟太久，管理员得手动重启插件 —— 这是刻意的（防刷屏）， 但值得在 UI 上说明。
